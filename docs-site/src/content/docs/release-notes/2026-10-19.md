Scion now mounts a repository's git metadata into agents so that an agent cannot change what git does for you or for other agents, while in-container git stays fully flexible. On Kubernetes, git projects that share one repository across agents are no longer supported; use a clone-per-agent workspace instead.

---

## Highlights

### 1. Agents Get Read-only Git Metadata and a Private `.git/config`

For worktree-per-agent and shared-workspace git projects, Scion mounts the repository's git admin surface into the agent read-only — `.git/hooks`, `.git/info`, `.git/objects/info`, and other agents' worktree admin directories — and gives each agent its **own private copy of `.git/config`**, bound read-write over the shared one. In-container git stays fully flexible: `git config --local`, `git push -u` and `branch --set-upstream-to` all work inside the agent, and their writes land only in the agent's own copy, never in your checkout or another agent's. On the Apple runtime, which cannot bind a single private file, the agent's `.git` is read-only instead, so in-container `git config --local` and `git push -u` upstream recording do not persist there. See [Workspaces](/scion/local/workspace/#git-that-scion-runs-on-the-host).

### 2. Kubernetes: One Clone Per Agent for Git Projects

On Kubernetes, git projects that share one repository across agents — worktree-per-agent, or a shared-workspace project on NFS — are not supported. Create such a project as **clone-per-agent**, where each agent gets its own clone of the repository, or run it on a local or Docker broker. An agent whose project would share one repository is refused at start with a message naming the remedy.

:::caution[Upgrade note]
Before upgrading, commit and push work from Kubernetes agents in git projects on NFS shared workspaces.
:::
