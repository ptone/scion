# Defect: IAP generates `services`-path audience for Cloud Run Instances, breaking invoker IAM

**Filed by:** Scion single-node design workstream
**Date:** 2026-08-26
**Component:** Identity-Aware Proxy (IAP) — audience generation for Cloud Run Instance backends
**Severity (to us):** High — forces `invokerIamDisabled: true`, eliminating defence-in-depth
**Related:** `defect-sandbox-delete-hang.md` (same workstream, different component)

---

## 1. Summary

When IAP is enabled on a Cloud Run **Instance** (`iapEnabled: true`), IAP generates
the `x-serverless-authorization` RS256 JWT with audience
`/projects/{number}/locations/{region}/services/{name}` — a **`services`** path. The
Instance's invoker IAM check expects either the Instance URL
(`https://{name}-{number}.{region}.run.app`) or an **`instances`** path
(`/projects/{number}/locations/{region}/instances/{name}`). The audience mismatch
causes the invoker check to reject the token with HTTP 401 regardless of IAM grants.

The same `services`-path audience appears in the `X-Goog-IAP-JWT-Assertion` ES256
JWT. That assertion's audience is an app-facing contract and we are **not** asking
for it to change (§8) — the defect is in `x-serverless-authorization` only.

**Consequence:** Operators must set `invokerIamDisabled: true` alongside
`iapEnabled: true` on Instances. This makes IAP the sole perimeter — the invoker
check cannot provide defence-in-depth. The 30–75 second reconciliation window after
a PATCH that enables IAP becomes a **fully open interval** during which the Instance
has no access control at all.

A second, related gap compounds this: **IAP does not create a per-Instance IAM
resource**, so access policies can only be set at the region level, not per-Instance.
Both gaps share a root cause: IAP models Instances as Services in its naming, but the
Instance-side machinery does not reciprocate.

## 3. The control matrix — this is the core of the report

### Control 1: Which audiences does the Instance invoker check accept?

Configuration: `iapEnabled: false`, `invokerIamDisabled: false` (both defaults).
Same SA (`scion-instance-gym`, holding `roles/run.invoker`), same Instance
(`q2-control`). Only the token audience varies.

| Variant | Token audience | Header | HTTP | Verdict |
|---------|---------------|--------|------|---------|
| **1a** | `/projects/721899303052/locations/us-east4/services/q2-control` | `Authorization` | **401** | **Rejected** |
| **1b** | `https://q2-control-721899303052.us-east4.run.app` | `Authorization` | **200** | Accepted |
| **1c** | `/projects/721899303052/locations/us-east4/instances/q2-control` | `Authorization` | **200** | Accepted |

The invoker check accepts **two** audience formats:
- The Instance URL (`https://{name}-{number}.{region}.run.app`)
- The `instances`-path (`/projects/{number}/locations/{region}/instances/{name}`)

It rejects the `services`-path. **1c is the critical detail:** the invoker check
already understands the `instances` resource path. If IAP generated it, the invoker
check would accept it.

### Control 4: Does the invoker check read `x-serverless-authorization`?

Same Instance, same configuration (IAP off, invoker on). Token placed in
`x-serverless-authorization` header with no `Authorization` header present.

| Variant | Header | Audience | HTTP | Verdict |
|---------|--------|----------|------|---------|
| **4a** | `x-serverless-authorization` | URL | **200** | **Accepted** — invoker reads this header |
| **4b** | `Authorization` (control) | URL | **200** | Accepted (known-good) |
| **4c** | `x-serverless-authorization` | services-path | **401** | **Rejected** — audience mismatch |
| **4d** | `x-serverless-authorization` | instances-path | **200** | Accepted |

**4a proves the invoker check reads `x-serverless-authorization` on Instances.** The
check works correctly — it verifies audience, checks IAM. 4c reproduces the exact
failure path: services-path audience in `x-serverless-authorization` → 401. 4d
confirms the fix: if IAP generated `instances`-path, the check would accept it.

**Important:** Controls 4a–4d were run with **IAP off** — the tokens were injected
directly by `curl`, not generated by IAP. This means `x-serverless-authorization`
set by an external client is **not stripped at the edge** before reaching the invoker
check. This is not a vulnerability (the token is still signature- and
audience-verified, so forging one buys nothing), but it is a non-obvious property of
the request path worth noting.

### Control 2: 401 vs 403 semantics

| Input | HTTP | Meaning |
|-------|------|---------|
| No auth header at all | **403** | No credential — IAM denial (Forbidden) |
| Token with wrong audience | **401** | Token presented, verification failed (Unauthorized) |
| Garbage bearer token | **401** | Token presented, unverifiable |
| Correct audience + authorized | **200** | Success |

The invoker check returns **401** ("The access token could not be verified") when a
token is presented but fails audience verification. It returns **403** when no token
is present at all. The IAP-on case is 401, confirming a token was consulted and
rejected at the audience-verification stage.

### Control 3: Confounder elimination

Clean reproduction on fresh Instance `q2-control`, not PATCHed from another
configuration:

| Step | Timestamp (UTC) |
|------|-----------------|
| `roles/run.invoker` granted to IAP SA (resource + project level) | 01:54:39 |
| Explicit IAM propagation wait | 180 seconds |
| `iapEnabled: true` PATCH | 01:57:39 |
| Full reconciliation (`CONDITION_SUCCEEDED`) | 01:59:24 |
| Additional buffer | 30 seconds |
| Probe sent | 01:59:54 |
| **Result** | **401** |

5 minutes 15 seconds between IAM grant and probe. No timing artefact, no
PATCH-ordering artefact, no IAM propagation artefact.

## 5. Second gap: no per-Instance IAP IAM resource

IAP enforces on Instances (edge-level 302 redirect works), but IAP's IAM surface
does not know Instances exist. `getIamPolicy` on the per-resource path returns 404:

| Resource | `getIamPolicy` result |
|---|---|
| Instance `iap-demo` (`cloud_run-us-east4/services/iap-demo`) | **404 NOT_FOUND** |
| Service `scion-hub` (`cloud_run-us-central1/services/scion-hub`) | **200** — policy + etag |
| Service `scion-discord` (`cloud_run-us-central1/services/scion-discord`) | **200** — empty policy + etag |
| Region `cloud_run-us-east4` (no service) | **200** — empty policy + etag |

`setIamPolicy` also 404s at the per-Instance path (verified directly on
`q2-control`, 2026-08-26T02:08Z). Access can only be granted at the **region
level** (`cloud_run-{region}`) or **project level**. This means all Instances in a
region share one access policy.

Note: the resource path `iap_web/cloud_run-{region}/services/{name}` is IAP's
convention — it uses `services` even for Instances. Zero Cloud Run Services named
`iap-demo` exist in the project.

### Tiered error masking (operator trap)

- Without `iap.admin` → **403** PERMISSION_DENIED (hides whether resource exists)
- With `iap.admin` → **404** NOT_FOUND (resource genuinely absent)
- `testIamPermissions` → succeeds (evaluates inherited project-level bindings, not
  per-resource policy)

An operator who checks `testIamPermissions` gets a positive result and concludes
per-Instance policies work. They don't.

## 6. Root cause — one sentence

**IAP models Instances as Services in its naming, but the Instance-side machinery
does not reciprocate.** The audience mismatch in `x-serverless-authorization` breaks
the invoker check (§3). The missing IAP IAM resource prevents per-Instance access
policies (§5). Both are the same modelling gap expressed at different layers.

## 7. Impact

1. **`invokerIamDisabled: true` is forced.** The invoker check cannot work with IAP
   on Instances. IAP at the edge is the sole perimeter. There is no
   defence-in-depth.

2. **The reconciliation window is a fully open interval.** When `iapEnabled` is
   toggled on via PATCH, there is a 30–75 second reconciliation period. During this
   window, if `invokerIamDisabled: true` is already set, the Instance has **no
   access control at all** — IAP is not yet enforcing, and the invoker check is
   disabled.

3. **Per-Instance access policies are impossible.** All Instances in a region share
   one IAP access policy (set at `cloud_run-{region}`). Fine-grained access control
   requires per-Instance IAP IAM resources.

4. **The documented IAP-on-Cloud-Run procedure is wrong for Instances.** The
   [documentation](https://cloud.google.com/iap/docs/enabling-cloud-run) says to
   grant `roles/run.invoker` to the IAP service agent. On Services, this works
   because the `x-serverless-authorization` audience matches. On Instances, the
   audience mismatches and the grant has no effect.

## 8. The fix, framed as narrow

**IAP should emit `instances` rather than `services` in the audience of
`x-serverless-authorization` (RS256)** when the backend is a Cloud Run Instance.

Control 1c and 4d prove the Instance invoker check **already accepts**
`/projects/{number}/locations/{region}/instances/{name}` as a valid audience. No
change is needed on the Instance side. The fix is entirely in IAP's audience
generation for the invoker-check token — when routing to an Instance backend, use
the `instances` resource path instead of `services`.

**The `X-Goog-IAP-JWT-Assertion` (ES256) audience should be left alone.** The
assertion's audience is a documented, app-facing contract — every IAP-protected
application verifies against that value. Changing it would break deployed
applications that have configured the current `services`-path string, to fix a
problem those applications do not have. The invoker check never looks at the
assertion; only `x-serverless-authorization` reaches it. The minimum fix changes
one token's audience, not both.

Separately, IAP should create the per-Instance IAM resource so that per-Instance
access policies can be set via `getIamPolicy`/`setIamPolicy`.

## 9. Why this matters to us

We are designing a single-node Scion tier where a Cloud Run Instance hosts the
control plane. IAP is the intended authentication perimeter (replacing a dedicated
auth-proxy Cloud Run Service). The invoker check staying active is important for
defence-in-depth (§S2 of our design), and per-Instance access policies are needed
for multi-tenant deployments.

Until the audience fix ships, our workaround is `invokerIamDisabled: true` with
careful PATCH ordering (enable IAP first, wait for reconciliation, then set
`invokerIamDisabled: true`) to minimise the open window. We'd rather not carry this.

## 10. What would help us most

1. Is the `x-serverless-authorization` audience mismatch known, and is a fix
   planned? The scope is narrow — one string in one token, and the Instance invoker
   check already accepts the correct `instances`-path format (Control 1c, 4d).

2. Is per-Instance IAP IAM planned, or is region-level the intended model for
   Instances? We need per-Instance access policies for multi-tenant deployments.

3. Is `invokerIamDisabled: true` under IAP the *supported* configuration on
   Instances today, or are we off the path? We'd like to know whether to build
   around it or wait for a fix.

4. Is there any way to close the reconciliation window? When `invokerIamDisabled:
   true` is set and IAP is being enabled, the 30–75 second reconcile produces a
   fully open interval. This is our sharpest operational exposure. An atomic
   enable, or a way to pre-configure IAP before the Instance accepts traffic,
   would eliminate it.

## 11. Provenance and limits

Produced during an empirical IAP spike (OQ-15) on real Cloud Run Instances —
deliberately not simulated, not against Services, not derived from documentation
alone. The audience-mismatch root cause was identified empirically, challenged with
four controls (audience acceptance matrix, 401/403 semantics,
confounder elimination, and `x-serverless-authorization` header processing), and
confirmed at each step.

**Limits worth stating:** single project, single region (us-east4), single day, two
Instances. We did not test whether Services exhibit the same behaviour (the
documentation says they don't, and the `getIamPolicy` comparison confirms Services
have the per-resource IAP IAM resource). We did not test other regions. The
`q2-control` Instance is held for re-probing; `iap-demo` is held as a live demo.

Raw output and full test matrix: `spike-iap-results.md`. Design consequences tracked
in `ac0-results.md`.
