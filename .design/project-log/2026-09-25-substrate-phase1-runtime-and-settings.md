# Project Log: Substrate Runtime Backend, Settings/Factory, and Broker-Side Home Delivery

**Date:** 2026-09-25
**Component:** `pkg/runtime/substrate*.go`, `pkg/runtime/substrate/` (ateapi dialer, router client), `pkg/config` (`V1SubstrateConfig`, `ValidateEgressAllow`), `pkg/runtime/factory.go`, `pkg/runtimebroker/handlers.go` (substrate-specific runtime-resolution and PTY-attach handling only)

See `.design/kubernetes/substrate-runtime.md` for the architecture and wire protocol as built; this entry records implementation decisions, gotchas, and defects found and fixed while building the runtime, settings, and factory wiring, plus the broker-side half of composed-home delivery.

## ateapi client vendoring

`go get`-ing `github.com/agent-substrate/substrate/pkg/proto/ateapipb` pulls its full `go.mod`, which requires a newer Go toolchain than this repo targets and forces major-version upgrades of `k8s.io/api`, `k8s.io/apimachinery`, `k8s.io/client-go`, and roughly a dozen other shared dependencies this repo already pins. The generated package itself (`ateapi.pb.go`, `ateapi_grpc.pb.go`, `ateapi.proto`, `source.go`) only depends on `google.golang.org/protobuf` and `google.golang.org/grpc`, both already present at compatible versions. Vendored verbatim under `third_party/ateapipb/` instead, with the source repo's license and the exact source SHA recorded in `README.md`, avoiding the transitive-dependency blast radius entirely.

## The dialer and router client (`pkg/runtime/substrate/`)

A minimal re-implementation of Substrate's own internal dialer (which scion cannot import), scoped to what an in-cluster broker needs:

- `Dial` opens a gRPC connection to ateapi Control, authenticated via `grpc.PerRPCCredentials` backed by a token source that mints (and caches, refreshing ahead of expiry) a bearer token for the *calling pod's own ServiceAccount* through the Kubernetes TokenRequest API. TLS is verified against a `ClusterTrustBundle` or a CA file; a config with neither is a hard construction error, not a fallback to unverified TLS — `InsecureSkipVerify` is never set anywhere in this path.
- The broker's own identity (namespace and ServiceAccount name) is read from the standard projected files, with the ServiceAccount name additionally cross-checked against the `sub` claim of the broker's own mounted token (decoded, not signature-verified — it only selects which SA to request a *new* token for; the TokenRequest API call itself is what's actually authorized). A namespace mismatch between the two sources is a hard error rather than silently trusting one.
- `RouterClient.Do` sends HTTP requests through `atenet-router` with the `ate-target-actor: <atespace>/<actor>` header. Each of `getHealthz`/`postBootstrap`/`doExec` sets its own context deadline (short poll, longer bootstrap, exec's own `timeout_s` plus slack) instead of sharing one blanket client timeout — an early version used a single flat client timeout that was shorter than the longest legal exec timeout, which would have aborted a legitimately long-running exec before it could finish.

## Settings and factory

`V1SubstrateConfig` lives under `V1RuntimeConfig.Substrate`; `pkg/runtime/factory.go`'s `"substrate"` case is reachable only when a profile explicitly names it — there is no auto-detect branch, unlike `docker`/`podman`/`cloudrun*`. A `substrate` sub-object was added to the `runtimeConfig` `$def` in `settings-v1.schema.json` (unlike `cloudrun_instances`/`cloudrun_sandbox`, which have none).

**Process-wide memoization, and the state-scoping bug it initially introduced.** The broker treats substrate as an *auxiliary* runtime: it re-resolves the runtime from settings on every `start`, not just once at broker startup. An early version rebuilt a fresh `*SubstrateRuntime` (including its `controlTokens`/`agentRecords` maps and a brand-new, never-closed gRPC `ClientConn`) on every such resolution — so a second agent's `Run` call would silently orphan the first agent's control token and connection, making it unmessageable. Fixed by memoizing one `*SubstrateRuntime` per distinct `V1SubstrateConfig` (a canonical JSON encoding as the map key) for the life of the broker process.

That fix was itself wrong on a second axis: keying *per-agent* state (control tokens, in-memory agent records) by config is correct for connections — a distinct config legitimately needs its own gRPC connection and CA — but wrong for per-agent state, because the broker re-resolves the "same" runtime from settings whenever anything about its config changes (an `egress_allow` edit, a second substrate profile, even the same settings re-serialized differently), and each such resolution is a different instance under config-keyed state. An agent started under the old resolution became unreachable via `Exec` under the new one. Fixed by moving per-agent state to *process-wide* maps (`substrateAgentRecords`, `substrateControlTokens`), shared across every `*SubstrateRuntime` instance regardless of which config resolved it; only the gRPC connection itself stays memoized per config.

A consequence, confirmed intentional: **the CA/trust material this memoization pins is fixed for the broker process's lifetime.** Rotating the CA behind the same `ca_file` path, or re-keying the same `ClusterTrustBundle` name, does not take effect until the broker restarts — the dialer's TLS config is built once, at first dial. A proper fix needs `GetConfigForClient`/`VerifyPeerCertificate` to re-read the CA source per handshake; not implemented in Phase 1 (documented as a known limitation).

**A second, structurally similar bug in the broker's own runtime-resolution shortcut.** `resolveManagerForOpts` (`pkg/runtimebroker/handlers.go`) resolves a requested profile's runtime *type* string and short-circuits to the default manager whenever that type equals the default runtime's `Name()`. That shortcut is correct for every other runtime (a broker only ever has one docker/k8s/cloudrun config at a time), but every substrate profile reports the same type string `"substrate"` regardless of its own distinct `V1SubstrateConfig` — so a second, differently-configured substrate profile (e.g. a different `egress_allow`) always silently got the *default* profile's manager and config back instead of its own. Fixed by never taking the type-match shortcut for substrate — no config-equality comparison either, since a comparison could itself drift out of sync with whatever actually determines a distinct instance; substrate always falls through to full `agent.ResolveRuntime` resolution, which the per-config memoization above already handles correctly. A side effect, confirmed intentional: the *default* substrate profile no longer necessarily gets the broker's own primary manager back either — it goes through the identical resolution path as any other profile, landing on the same memoized `*SubstrateRuntime` wrapped in a fresh `agent.NewManager`. `resolveAgentRuntimeTarget`'s own lookup already tries every manager rather than picking by type, so no changes were needed there — per-agent state and the backing `ListActors` call are process-/cluster-wide, not scoped to which manager instance issued a given `Run`.

`SubstrateRuntime.Name()` is a hardcoded literal, `"substrate"`, that never consults its own config — so a differently-named settings profile can never change what the broker's own substrate-specific checks (the runtime-resolution shortcut-skip above, and the PTY-attach clean-error path) see. This is deliberately verified end to end (via the real `config.LoadEffectiveSettings` → `ResolveRuntime` → `NewSubstrateRuntime` path, for two differently-named profile entries), not just asserted from reading the one-line method, since it's exactly the property those checks depend on to engage at all for a non-default-named profile. Delete/stop resolution (below) does not check `Name()` at all — `resolveDeleteTarget`/`projectScopedTarget` scope by project ID uniformly, on every runtime.

## The `Run` sequence and ActorTemplate content-addressing

`Run` executes the nine steps in `.design/kubernetes/substrate-runtime.md` §4: atespace creation, the digest-pin check, template ensure/wait-ready, actor creation, egress policy creation, resume-and-wait-running, healthz poll, bootstrap, and returning the runtime ID. Any failure from `CreateActor` onward triggers best-effort cleanup (delete the actor and its egress policy) on a fresh, short-lived context before returning the original error.

**The atespace name needs sanitizing, not just truncating.** `substrateAtespaceName` (`"scion-"` + the first 12 characters of `projectID`) initially assumed that prefix was already a valid Kubernetes short name. It now runs through a K8s short-name sanitizer (`sanitizeK8sShortNameFragment`) — lowercase, non-alphanumeric/hyphen replaced, leading/trailing hyphens trimmed — rather than trusting the project ID's own alphabet.

**`CreateActor`'s `AlreadyExists` needs to look like every other runtime's "name in use" error, without a new import.** `pkg/agent` imports `pkg/runtime`, so `pkg/runtime` returning `pkg/agent`'s own `ErrContainerNameInUse` directly would cycle. Every runtime's launch-error classification instead pattern-matches the *text* of any runtime's `Run` error (looking for phrases like "container name" + "already in use"). `SubstrateRuntime`'s `AlreadyExists` error is worded to match that pattern deliberately, so the existing broker handling applies without any new coupling.

**Template content-addressing covers more than the image alone, and needs to.** `substrateTemplateName` hashes image digest, sandbox class, sandbox config name, worker selector, snapshot storage, the *effective* resources (a nil `*ResourceSpec` is resolved against the built-in default before hashing — hashing a nil pointer as empty would let a future change to that default silently reuse a stale golden template), the hardcoded snapshot scope, the container's added capabilities, and an entrypoint-protocol version, with `egress_trust_bundle` appended as its own hash segment only when non-empty (so a plain install's existing golden templates stay byte-identical and reused, while setting it always produces a new name, since `buildActorTemplate`'s output genuinely differs). Every one of these fields is real `ActorTemplate` content `buildActorTemplate` bakes in; omitting any of them from the hash would mean changing it in settings (or, for the capability set, in this runtime's own code) silently reuses a stale golden snapshot that doesn't reflect the change — exactly the failure class a second substrate profile's ignored `egress_allow` (above) was one instance of, and the capability-set change (see the substrate-serve/sciontool log) was another.

## `List` and the record-less / same-slug story

Substrate actors carry no labels of their own (confirmed from the proto), so `AgentInfo` fields are synthesised from an in-memory, per-actor-UID record populated at `Run`. This went through several iterations before landing on its current, deliberately conservative shape:

1. **Original defect: `List` reported the actor's full Substrate resource name (`<project>--<agent>`) as `AgentInfo.Name`, not the bare agent slug** the broker's delete path matches against. `scion delete` therefore never found a match, silently no-opped, and reported success while the actor kept running. Fixed by using the in-memory record's real slug when one exists, matching Docker's own `List` convention (label first, raw name only as a fallback).
2. **A record-less actor (e.g. after a broker restart lost its in-memory record) still needs *some* name to report.** An attempt to recover the agent slug by inverting the naming scheme (splitting the actor's resource name on its separator) was implemented, hardened against multiple ambiguous splits, and then found to still be exploitable: verification of the recovered slug only happened when the calling lookup's own filter happened to carry a project-scoping key, but the broker's actual delete/stop code paths list agents unscoped by project and post-filter in broker memory — so a record-less actor in one project could resolve, and be deleted, through a same-slug request scoped to a *different* project. **Decision: remove the recovery entirely, rather than extend it further.** A record-less actor now reports its own full resource name as `"scion.name"`, exactly as it did before any recovery was attempted — a real agent slug can never equal that (it always contains the naming separator, which a slug never does), so no slug-based query can ever match a record-less entry, structurally, regardless of which broker code path or project scope is involved. The accepted cost: a record-less actor cannot be stopped, deleted, exec'd, or have its logs read by slug at all, until its record is somehow restored or an operator intervenes directly against the cluster — a no-op is an acceptable failure mode here; a wrong-actor action is not.
3. **Two record-*having* actors can also collide on slug, across different projects**, once fix (1) made `List` trust a record's own slug directly. `List` never populated `AgentInfo.ProjectPath` at all, so a project-scoped broker-level delete always resolved an empty project path downstream, which meant the broker's own project-matching check never engaged, and an unscoped or wrongly-scoped delete could hit either project's same-slug actor depending on listing order. Fixed in two parts: (a) `Run` now reads the project path off the same annotation every other runtime's `Run`/`List` already uses, and stores it on the in-memory record, so `List` can populate `ProjectPath` correctly for a *scoped* lookup; (b) `List` also tallies record-having actors by slug and, when a query with no project-scoping key in its filter matches more than one record-having actor, excludes all of them from the result rather than guessing — a defense-in-depth guard for any caller that lists by bare slug alone. This only ever engages when a slug genuinely collides across projects (rare); the ordinary single-project case is completely unaffected.
4. **Delete and stop are now resolved project-scoped from the first `Runtime.List` call, on every runtime, not just substrate.** `resolveDeleteTarget` and `projectScopedTarget` (`pkg/runtimebroker/handlers.go`) include the requested project ID in the filter passed to `Runtime.List`/`LookupContainerID` itself, so the query returns only the requested project's entries directly — fix (3)'s guard never has a reason to engage on this path, since the filter already carries a project-scoping key. The resolved entry's own container ID (for substrate, the globally-unique `<atespace>/<actor>` pair) is what `Manager.DeleteTarget`/`Manager.Stop` act on, so the runtime-level call never lists by bare slug again either. A project-scoped request with no matching agent in that project — checked against the runtime listing, a legacy no-project-identity fallback, and the project's own file-only directory — resolves to `errDeleteTargetNotFound`, answered as `404`; the hub's broker clients already treat a `404` on delete as an idempotent success (`pkg/hub/controlchannel_client.go`'s `DeleteAgent`, `pkg/hub/broker_http_transport.go`'s `DeleteAgent`), so no substrate-specific status-code handling is needed on either side.

## Egress: `egress_allow` validation hardening

`ValidateEgressAllow` is allowlist-first: only public FQDNs (optionally wildcarded) pass; everything else — IPs/CIDRs in any form, catch-alls, non-ICANN top-level domains, Kubernetes-internal-shaped names, a hostname that is itself a public suffix — is rejected. The validator was hardened iteratively against concrete bypasses found by direct, adversarial testing against the implementation, not just spec reading:

- **Alternate spellings of the same forbidden thing evaded the checks that already existed.** A trailing-dot FQDN defeated suffix matching that assumed no trailing dot; Kubernetes short names resolvable through the in-cluster DNS search path (a bare, single-label-plus-namespace form) were never rejected because they don't look like any blocked suffix; non-canonical IP spellings (hex, decimal, IPv4-mapped, zone-ID-suffixed, port-suffixed) all fell through to the hostname-validation path, where nothing recognized them as addresses at all. Fixed with an explicit normalization pass (trim, lowercase, strip one trailing dot) before any check, explicit rejection of bracket/percent/malformed-CIDR/malformed-bare-IPv6 shapes, explicit rejection of numeric-IP-alias-shaped strings, explicit rejection of single-label hostnames, and rejection of any hostname whose top-level domain is not an ICANN-delegated public suffix (`egressAllowSuffixOK`), which replaced an earlier known-namespace/hyphenated-TLD heuristic.
- **A rejection can be "correct" by accident, through the wrong rule, with a message that describes the wrong reason.** A wildcard's single-label remainder was, after one fix, correctly rejected — but by a *different* check than the one that should have fired, with a misleading message. A test suite that only asserts "an error occurred" cannot catch this class of drift; the regression table was changed to assert the specific rejection *reason* (one of a fixed set of named reason constants, each tied to exactly one rule in the validator) for every row, not just that validation failed. A tautological variant of the same gap was later found in two individual tests that matched on a bare word (e.g. "arpa") that also appears, coincidentally, inside the echoed input itself — tightened to match the actual reason phrase instead.
- **The threat model this validation protects is in-cluster reach, not restricting how broad an operator's own external allowlist is.** Proposals to require multiple non-wildcard labels or cap public-range CIDR/wildcard breadth (e.g. rejecting `*.com`) were deliberately declined for Phase 1: `egress_allow` is operator-configured, not attacker-controlled input. Revisit only if entries are ever sourced from something less trusted than an operator's own settings.
- `ValidateEgressAllow` rejects every IP address or CIDR outright, in any spelling (`looksLikeIPAttempt`); there is no separate blocked-range list. Class E/reserved (`240.0.0.0/4`), 6to4 (`2002::/16`), and NAT64 (`64:ff9b::/96`) ranges are covered by that same reject-all-IP rule and appear in the test suite as regression rows for it, the latter two because they embed IPv4 address space that must not bypass the IPv4 checks.
- **Documented, not closed:** none of this validation defends against a validly-public hostname later resolving to a private or in-cluster address (DNS rebinding, or a service like nip.io/sslip.io that maps arbitrary text to an IP by design). Closing that needs a post-resolution check by the egress proxy itself, which Phase 1 does not add.

The validator's own doc comment carries the exact rule set rather than restating it here, since the rules change independently of this log.

## `egress_trust_bundle` (sdsmint MITM gateway support)

Live diagnosis on the target cluster found every actor's outbound HTTPS failing even with a correct `egress_allow` — Substrate's plain egress gateway only enforces `egress_allow`'s hostname rules for HTTPS under the **sdsmint** gateway variant, which MITMs every TLS connection with its own per-SNI certificate. An actor validating only public roots rejects that certificate.

`egress_trust_bundle` (a string, not a bool, deliberately — it mirrors Substrate's own trust-bundle-name field, so a future second supported name needs only an allowlist entry) is validated against a one-name allowlist (only `egress-mitm.ate.dev`, the one name the vendored Substrate version resolves) by `V1SubstrateConfig.Validate`, called from `NewSubstrateRuntime` and again from `Run` — not at settings-load time or by `scion config validate` — so a typo fails fast with a clear message instead of failing much later, opaquely, at actor start. When set, `buildActorTemplate` projects the gateway's CA into the actor via a `system-info` volume and points a fixed set of CA-bundle env vars at it — `pkg/substrateenv.TrustBundleVarNames` is the single shared list of names, imported by both `buildActorTemplate` (which sets them) and the substrate-serve exec path (which must preserve them across a `su -` login shell — see the substrate-serve/sciontool log), so the two can't silently drift apart. Leaving it unset is byte-identical to before the field existed (no volume, no mount, no env, no hash-input change); setting it on a plain, non-sdsmint install breaks every actor at start rather than merely losing HTTPS, since nothing backs the named `ClusterTrustBundle` there — documented plainly rather than guarded against, since guarding against it would require the runtime to know things about the cluster it has no way to check.

`ateapipb.VolumeMount` has no `ReadOnly` field at all, so the trust-bundle mount this projects is read-only by construction — there is no mode to accidentally set writable.

`SSL_CERT_DIR` is set deliberately alongside the four more commonly expected CA env vars: it makes the gateway CA *exclusive* for Go and Python's default certificate lookup (both replace their default search path rather than adding to it), which is what makes sciontool's own hub connection a meaningful, fail-closed proof that traffic actually went through the gateway. It is only additive (or entirely ignored) for curl, git, and Node, each for a different underlying reason — documented in full in `deploy/substrate/README.md` rather than restated here, including how to force a stronger proof for curl specifically.

## Broker-side home delivery

`buildBootstrapFiles` originally shipped only `ResolvedAuth.Files` and file-type `ResolvedSecrets` — the broker-composed agent home (harness-config `home/`, the resolved template home, skills) was never part of the bootstrap payload at all, unlike Docker (bind-mount) or cloudrun-sandbox (relocate). The live symptom: the harness sat on its first-run setup prompt, because none of the harness-config's own home files — the ones that suppress that prompt — ever reached the actor.

`homeBootstrapFiles(homeDir, containerHome)` walks the home directory with `filepath.WalkDir`, which reports a symlink's type without ever descending into it — regular files only; symlinks, fifos, sockets, and devices are skipped and counted, never read. `buildBootstrapFiles` assembles the wire payload in precedence order — home files first, then auth files, then file-type secrets — and dedupes by final path with the *later* source winning, so exactly one entry per path reaches the wire regardless of how many sources target it; auth and secret files always override a same-path home file. Every path (home, auth, and secret alike) is `filepath.Clean`ed before dedup, since two differently-spelled but equivalent paths (e.g. a doubled separator) previously could have produced two wire entries for what should have collapsed to one.

**Total size cap, sized from a measured limit, not an assumed one.** Before choosing a number, the actual transport was checked rather than guessed: the router's ingress listener for this route has no request-body cap of its own anywhere in its filter chain (the 1 MiB `per_connection_buffer_limit_bytes` default there is a flow-control watermark, not a cap — the body streams through uninspected under a 300-second route timeout). The binding limit is `sciontool substrate-serve`'s own handler, which bounds the raw request body via `http.MaxBytesReader`. `maxBootstrapFilesTotalBytes` (16 MiB decoded, checked once against the deduped set's summed size, tracked per-entry rather than re-decoding base64 to check) is sized with roughly 3x headroom under that serve-side limit even after accounting for base64's 4/3 expansion and the surrounding JSON envelope. `homeBootstrapFiles` also tracks a running total *during* the walk itself and can return the same cap error early, before reading an oversized file into memory — a conservative early exit that can count a home file against the cap even when a same-path auth/secret file will later override it and win dedup; the post-dedup check in `buildBootstrapFiles` remains the authoritative one, and this early-exit behavior is an accepted, documented trade-off rather than a bug.

**Hygiene:** home file contents (a harness settings file can carry env-shaped values) are treated as secret-grade — never logged or put in an error on either side of the bootstrap hop — but this doesn't narrow the existing exposure: the composed home rides the same plaintext broker→router hop that auth and secret files already ride in the Phase 1 fixture. The skipped-non-regular-entries log line is capped to the first 20 relative paths plus a total count, so a home directory with an unusually large number of skipped entries can't produce an unbounded log line.

The serve-side half of this work — the path-safety symlink guard, the two stable rejection codes, and the transport-limit-signaling switch to `http.MaxBytesReader` — is documented in the substrate-serve/sciontool component log, since it lives entirely in `pkg/sciontool/substrate/`.

## Broker-restart false-success fix (ptone/scion#1808)

**The problem.** The `List`/record-less-actor story above (see "record-less / same-slug story") already made a record-less actor structurally unreachable by slug — never a wrong-actor action. It left one gap: with no in-memory record to check against, a project-scoped delete/stop for an absent slug is indistinguishable from "genuinely nothing here," and the generic path answers that as the ordinary idempotent 404/202. Right after a broker restart, that idempotent answer can be false — the actor a caller meant may still be running, along with its egress policy and worker — and the hub treats a 404 on delete (and a 202 on stop) as a completed operation, orphaning all three with no further signal.

**The record-less probe.** `SubstrateRuntime.RecordlessActors(ctx, projectID)` (`pkg/runtime/substrate_runtime.go`) lists the actors in `substrateAtespaceName(projectID)` — scoped both via `ListActorsRequest.Atespace` and a defensive atespace-equality check on the returned actors, since the test fake (and possibly a real server under some conditions) may not honor the request-level scope — and returns the name and UID of any actor there with no `substrateAgentRecords` entry, excluding one already in `ACTOR_STATE_DELETING` (below). `pkg/runtimebroker` declares the `RecordlessActorProber` interface it needs and type-asserts an `agent.Manager`'s underlying `runtime.Runtime` against it — never added to the generic `Runtime` interface, so docker/k8s are structurally unaffected, the assertion simply fails for them. Scoping the list to a project's own atespace is the whole exclusion rule for what counts as an agent actor: `CreateActor` (`Run`) is the only call site that creates an `Actor` there, one per real agent; a template's golden actor lives in the Substrate-reserved `ate-golden` atespace instead (per the vendored proto's own `DeleteActorTemplate` doc comment), and `ActorTemplate`/`Tag` are distinct resource kinds `ListActors` never returns at all — no separate "is this actor substrate-internal" check is needed. `resolveDeleteTarget` and `stopAgent` each consult the probe only when the caller supplied a project ID and only at the point they would otherwise report the idempotent outcome: at least one record-less actor there turns the answer into `HTTP 409 substrate_agent_identity_unknown` (`ErrCodeSubstrateAgentIdentityUnknown`, `SubstrateAgentIdentityUnknown`) instead, naming only the atespace and the count in the response body; a probe error is an explicit 5xx, never treated as "none found." The response body's count-only shape is a deliberate public-disclosure limit — the actor names themselves are logged at WARN in the broker's own log only, on both the delete and stop 409 paths (delete's `agentIdentityUnknownError` carries them out of `resolveDeleteTarget`; its own `Error()` still reports only the count and atespace, so nothing about the type changes what a caller sees).

**Paths closed.** On the delete path, the probe runs on every "no runtime entry matched" outcome, ahead of the local-file fallback (`findAgentProjectDir`) rather than only after that fallback also finds nothing: `AgentManager.DeleteTarget` skips the runtime entirely for a file-only target, so on a broker whose project directories survive a restart (a workstation, or any `$HOME` not wiped along with the container filesystem the way this deployment's is), the fallback could otherwise resolve a file-only delete target for an agent whose actor is still running, record-less, on the cluster — reporting success, removing only the files, and orphaning the actor, its egress policy, and its worker. On the stop path, `projectScopedTarget`'s generic error-swallowing (collapsing any `LookupContainerID` error, transient or genuine not-found alike, into the same `""`) is closed by using an error-preserving lookup instead, on the prober path only (below); the generic helper itself, and every runtime without the prober capability, is unaffected.

**The single error-preserving lookup.** `projectScopedTargetErr` and the auxiliary-runtime scan it uses, `auxListAgentsSorted`, return `errLookupListFailed`-wrapped errors instead of swallowing a list failure. Auxiliary runtimes are scanned in the same fixed, sorted order `allManagers()` already uses (not Go's randomized map order), and the scan continues past an auxiliary list error rather than stopping at the first: a match found on any auxiliary runtime is authoritative even when another one errored. The governing rule is 5xx exactly when the lookup cannot determine the target — a primary-list error, or a stage that ends with no match after any auxiliary list error (so an auxiliary list error in the project-scoped stage is decisive on its own, even though the unscoped fallback stage, not run in that case, might have matched). This decides from this one call's own outcome; there is no second, independent list call to fall back on, because a second call can spuriously succeed after the first call's transient failure and mask exactly the failure this mechanism exists to catch.

**Stop dispatch through the manager that produced the match.** `auxListAgentsSorted` and `projectScopedTargetErr` also return the `agent.Manager` whose `List` call actually produced the matching entry — the default manager for a primary- or fallback-stage match, or the specific auxiliary manager for an aux-stage match — and `stopAgent` dispatches `Stop` through that same manager instead of re-deriving one from a second, independent lookup (`resolveManagerForAgent`/`resolveAgentRuntimeTarget`, which re-lists auxiliary runtimes in map order and has no relationship to which runtime the already-resolved target came from). With two auxiliary runtimes both holding a project-matched agent for the requested slug, that second lookup could otherwise send the container ID found on one runtime to the other runtime's `Stop`. The non-prober path (`LookupContainerID`/`resolveManagerForAgent`/`projectScopedTarget`) is untouched, confirmed byte-identical function by function.

**UID dedupe.** `recordlessActorProbe`'s results are deduped by actor UID, not by atespace/name: the atespace/name pair is derived only from `projectID` and is therefore identical across two different ateapi endpoints, so two distinct substrate managers on different endpoints reporting a same-named actor in the same atespace name would otherwise collapse into one entry, under-reporting the count and hiding one actor's name from the operator. A record-less actor reported with no UID (a defensive-only branch; a real actor always carries one) falls back to an atespace/name key and is still counted.

**Paging cap.** `RecordlessActors`' `ListActors` page cap, `maxRecordlessActorListPages`, is a package variable rather than a constant so a test can lower it; both the page cap and the repeated-token guard have tests, plus a test pinning that the probe walks every page rather than stopping at the first.

**The `DELETING` exclusion, qualified.** A record-less actor already in `ACTOR_STATE_DELETING` is excluded from the count: `DeleteActorEgressPolicy` already runs before `DeleteActor` in `Delete` (§9), so a `DELETING` actor's egress policy is already gone and there is nothing left worth protecting against the egress leak this mechanism exists to prevent. The proto documents no transition back out of `DELETING` to a live state either — `RevertActor`, the one RPC that returns an actor to a pre-delete state, only accepts CRASHED/RUNNING/PAUSED actors (`third_party/ateapipb/ateapi.proto:46-47`), and `ActorStatus.state` is required on every listed actor, so a listed actor's state is never zero-valued/unknown. This is not free: a pre-restart actor can legitimately be sitting in `DELETING` at restart time — for example, one this same broker began deleting (`Stop` is `Delete` in Phase 1) just before the crash that triggered the restart, whose deletion then never finished — and the exclusion does not distinguish that case from the no-restart stop-then-delete race it exists to prevent. A delete of that actor's slug afterward returns the ordinary idempotent 404, and the hub drops its agent record, while the actor may still exist, stuck, in the cluster; accepted as trade-off (d) below, since a process-local record of this broker's own delete requests could not tell the two cases apart either — why the deletion never finished is below scion, not something this process tracked.

**Trade-offs**, documented in full in `deploy/substrate/README.md`'s "After a broker restart" section, (a)-(d): (a) `substrateAtespaceName` truncates a project ID to its first 12 (sanitized) characters, and project IDs are client-supplied at hub project creation (`pkg/hub/handlers_projects_core.go`), so an operator who knows another project's ID prefix can deliberately create one that collides — disclosing only a count of record-less actors in the colliding atespace and forcing 409s on that project's genuinely-absent-slug deletes/stops, never a wrong-project action, since the probe only ever turns a would-be success into an error; (b) once at least one record-less actor exists in a project's atespace, every delete or stop of an absent slug in that project returns 409 instead of the usual idempotent 404/202, until every record-less actor there is cleaned up; (c) a narrow window between `CreateActor` succeeding and this process recording it (spanning `waitRunning`, `healthz`, and bootstrap) makes a new actor look record-less to a concurrent delete/stop of an unrelated absent slug in the same project, or of the in-flight agent itself — both get a spurious 409, never a wrong action; (d) the `DELETING` exclusion above.

**Hub-side error mapping differs between the two paths.** `pkg/hub/handlers_agents_core.go`'s delete handler re-codes a broker 409 as the hub's own `conflict` status (checking `brokerStatusError.StatusCode == http.StatusConflict`); `pkg/hub/handlers_agent_lifecycle.go`'s stop dispatch (`AgentActionStop`) has no equivalent check, so every `DispatchAgentStop` error, this one included, reaches a CLI caller as a generic 502 `runtime_error`. `ErrCodeSubstrateAgentIdentityUnknown`'s doc comment documents both paths rather than describing only delete's.

**The runbook.** `deploy/substrate/README.md`'s "After a broker restart" section: identify the actor from the broker's own WARN log line, which lists every record-less, non-`DELETING` actor in the atespace and so routinely includes other, undamaged pre-restart agents in the same project — derive the one actor name the delete/stop in hand is actually for (`<project-slug>--<agent-slug>`, the same `containerName` convention `pkg/agent/run.go` uses) and act only on that name if it appears in the line; confirm its creation time predates the broker **container's** own start time (`state.running.startedAt`, which moves on every process restart, unlike the pod's own `.status.startTime` under `restartPolicy: Always`); cross-check it against the hub's own agent list; delete its egress policy first via a direct `grpcurl` call to the ateapi Control service's `DeleteActorEgressPolicy` (TLS verification on, authenticated with an exported `ATE_TOKEN` that `grpcurl -expand-headers` substitutes into the header itself so the token reaches neither argv nor disk) and verify `GetActorEgressPolicy` returns `NotFound` before proceeding; delete the actor `--any-state`; then force-delete the hub's own agent record via a direct API call — `force=true` still dispatches to the broker exactly as an ordinary delete would and only changes what happens when that dispatch fails, it does not skip the broker — with the token read via `read -rs`, held only in a 0600 temp file guarded by an `EXIT` cleanup trap paired with a separate `INT`/`TERM` trap that exits (so an interrupt stops the block instead of falling through to the next command), and `curl --fail-with-body` so a rejected request cannot be mistaken for a completed step. `scion delete --force` does not exist as a CLI flag.

**Tests.** Coverage spans: the probe's atespace scoping and `DELETING` exclusion; both the delete and stop paths turning an unresolved target into the 409 only when a `RecordlessActorProber` is registered and a project ID is present, and leaving every other combination at the generic idempotent behavior; the 409 response body carrying only the atespace, count, and remedy pointer, for both delete and stop, never an actor name; the WARN log carrying the names on both paths; `projectScopedTargetErr`'s sorted, error-preserving auxiliary scan, including a transient list failure never being masked by a second call, an auxiliary list error being decisive per the 5xx rule above, and — with two auxiliary runtimes, one matching and one erroring — the sorted-order resolution and its returned manager both being pinned, not just the returned container ID; `stopAgent` dispatching through the manager that produced the match, for a match on the default runtime at either stage and for an unlabelled match found only by the auxiliary fallback scan; project isolation on the prober stop path at both the primary and the auxiliary lookup stage; a prober registered only as an auxiliary runtime (not the broker's default) still being probed on the delete path; the page-cap and repeated-token guards, and that the probe walks every page; UID dedupe, including the no-UID fallback; `RecordlessActors` reading the shared in-memory record map under the same lock a concurrent `Run`/`Delete` writes it under, exercised under `-race`; and a broker-level stop of a new agent created after a restart, through the broker's own `stopAgent` handler. `deploy/substrate/broker.yaml`'s ConfigMap repoints `profiles.local`/`profiles.remote` at the broker's own `substrate-prod` runtime, so `discoverAuxiliaryRuntimes` (`pkg/runtimebroker/server.go`) registers neither docker nor Kubernetes as an auxiliary runtime on this broker; `pkg/config`'s `TestLoadVersionedSettings_SubstrateBrokerProfiles_NoDockerOrKubernetesRuntimeType` verifies a hand-maintained copy of the ConfigMap's settings stanza resolves every profile to the substrate runtime type, and `TestDeploySubstrateBrokerYAML_SettingsHaveOnlySubstrateProfiles` parses the real manifest file directly so the two can't silently drift apart.

## Error hygiene

Every `Run` error path that could carry request/response content is routed through a redaction helper before it can reach a returned error string, reusing the shared `redactEnvValues` substitution helper, with its own candidate set. This needed extending twice beyond its original scope: once to cover `ResolvedAuth.EnvVars` and both env- and file-type `ResolvedSecrets` (not just the base config env the helper was originally written for), and once more to key redaction candidates by `"<source>:<name>"` rather than bare name, since two different sources can legitimately share a name (e.g. a file-type secret and an env var both called the same credential name) and would otherwise silently collide in the redaction set, dropping coverage for one of them. `ResolvedAuth.Files`' own contents (credential JSON/tokens read from disk) are a redaction candidate too — an earlier version's stated intent to cover "bootstrap file contents" had never actually been wired up.

## Wipe-hook production-reference guard

`WipeSubstrateAgentStateForTest`'s guard test (which fails the build if the symbol is ever referenced outside a test file) skipped any non-test line starting with `func WipeSubstrateAgentStateForTest`, which would also skip a longer identifier's declaration sharing that prefix even when it called the real symbol later on the same line, and it exempted every comment line unconditionally, which would miss a `//go:linkname` directive naming the symbol. The line-scanning logic is a small pure function with its own tests pinning both gaps, alongside the two shapes that must not false-positive (the real declaration, and ordinary doc-comment prose mentioning the symbol), in addition to the existing whole-module scan.
