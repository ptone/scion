# Project Log: `sciontool substrate-serve` Control Server, Privilege Drop, and Rootfs Fixups

**Date:** 2026-09-25
**Component:** `cmd/sciontool/commands/substrate_serve.go`, `cmd/sciontool/commands/substrate_rootfs.go`, `cmd/sciontool/commands/init.go` (substrate-specific precondition checking only), `pkg/sciontool/substrate/*`, `pkg/substratecaps`, `pkg/substrateenv`

See `.design/kubernetes/substrate-runtime.md` §5 (bootstrap protocol and control server), §5.5 (path safety), §5.6 (SIGTERM), and §8 (privilege drop and rootfs) for the architecture and contract as built. This entry records the implementation decisions, live-incident root causes, and test-hermeticity lessons behind that design — several of them non-obvious differences between Substrate's actor environment and every other runtime's assumptions, and worth preserving in detail since they will recur if this control server is ever ported elsewhere.

## The control server itself

`sciontool substrate-serve` is a new Cobra subcommand, ships in the same binary as every other `sciontool` command with no image-build change needed, and is PID 1 inside the actor. `RunInit` (the same function `sciontool init` uses) was refactored to take an options struct rather than being called directly, so substrate-serve can reuse it in-process — through an injected `InitRunner` function value — instead of forking a second implementation. The one behavioral parameter substrate-serve needs from `RunInit` is `ForwardTermSignal: false`: substrate-serve owns SIGTERM handling itself (see below) and must not have `RunInit` install its own competing signal handler underneath it.

The autoexpose reconciler and the hub port-forward tunnel manager (both WebSocket-based) are skipped entirely when `SCION_RUNTIME=substrate`, set in the bootstrap env: Substrate's egress is HTTP(S)-only and default-deny, so leaving either running would just spin retrying a gateway that always refuses the protocol upgrade.

**Bootstrap file writes.** `mkdirAllTracked` returns exactly the directories it created (not the ones that already existed), so the handler chowns only what it made, never a pre-existing ancestor. `os.WriteFile`'s mode argument only applies to a file's *creation* — it has no effect on a file that already exists at that path (a plain overwrite leaves the existing mode untouched), and is subject to the process umask even then. A bootstrap request asking to tighten an image-baked, world-readable credential file to `0600` therefore silently failed to do so. Fixed with an explicit `os.Chmod` after every successful write, so the requested mode always wins regardless of umask or a pre-existing file — proven with a Prove-It-style test (pre-create the file at a looser mode, bootstrap a tighter one, assert the final mode) that was confirmed to fail without the fix.

**Exec.** `runExec` shells a command through the same exec-as-user wrapper other runtimes use, but is a deliberate, documented duplicate rather than a shared import: `pkg/sciontool` (the in-actor binary) must never import `pkg/runtime` (confirmed transitively pulls in `pkg/config`, which would break an existing test canary asserting the in-container binary never does project-path resolution). Extracting a shared leaf package for the ~10-line wrapper is flagged as a natural follow-up once both sides of this branch's work are stable, not done unilaterally mid-implementation. Output is captured through a writer that hard-stops at a fixed per-stream byte cap and flags truncation independently for stdout/stderr.

**A process-group/cancellation gotcha specific to how the wrapper re-execs.** The exec wrapper re-execs into a fresh `sh -c "$cmd"`; the build image's `/bin/sh` is `dash`, which does **not** tail-call-exec a simple last command (e.g. `sleep 30`) — it forks a real child with a different PID. `exec.CommandContext`'s default cancellation only signals the top-level tracked PID, so a timeout would have left the actual work running to completion, orphaned, regardless of the request's own deadline. Fixed by giving the command its own process group and killing the whole group (negative PID signal) on cancellation. Caught by a real-subprocess test asserting a `sleep 30` under a ~300ms timeout actually dies within that window, not after the full sleep.

## Bootstrap path safety: the every-component symlink guard

`writeBootstrapFile` accepts arbitrary absolute paths from the bootstrap payload. The parent-directory creation logic went through three iterations before landing on a guarantee that actually holds:

1. **Original:** find the deepest existing ancestor via `os.Stat` (follows symlinks), delegate the rest to `os.MkdirAll` (also `Stat`-based). An image shipping a pre-existing symlink at an intermediate path component (e.g. a config directory symlinked to a system directory) is silently written *through*: `Stat` reports the link's target as an ordinary existing directory, and the remaining components get created on the far side of it. Confirmed exploitable by test before any fix existed.
2. **First fix:** walk *upward* from the target directory with `os.Lstat` (never follows) to find the deepest already-existing ancestor, then create only the missing suffix with plain `os.Mkdir`. This closes the case where the symlinked component's target is missing the remaining subpath — but not the case where it isn't: an upward walk that stops at the first existing ancestor never Lstats anything *above* that point, so a symlinked component further up the path, whose target already happens to contain the rest of the subpath, is never noticed at all.
3. **Actual fix:** Lstat *every* existing component of the cleaned target directory, top-down from the first component to the target itself — not just the deepest one that happens to exist. The first symlink found anywhere in that walk rejects the whole write, naming only its own path. The first missing component marks the start of a suffix created top-down with plain `os.Mkdir` (never `os.MkdirAll`, which would reopen exactly the same hole one level down). Every directory `os.Mkdir` creates under this scheme is therefore known-real by construction, not merely assumed to be.

This is a plain existence-check-then-create, not one atomic operation, and the code says so: it is safe only because nothing writes concurrently during bootstrap (substrate-serve is the sole writer, and the harness has not started yet), and it is **not** a general TOCTOU-safe guarantee.

The leaf file itself needs no such walk: the atomic-write helper's final rename replaces whatever directory entry currently sits at the target path — including a pre-existing symlink — rather than following it, so a symlink at the leaf is safe by construction (atomically replaced, its old target left untouched).

A related, easy-to-miss gap: the parent-directory walk used a cleaned path, but the final write originally used the caller-supplied path raw. A `..` segment in an uncleaned path is resolved by the kernel at syscall time against whatever is physically on disk — which does not necessarily agree with the lexically-cleaned directory the symlink walk just validated, if an earlier component is itself a symlink. Fixed by cleaning the path once, up front, and using that single cleaned value for both the walk and the final write target, so the two can never disagree about what they're each checking versus writing.

**The guard applies to every bootstrap file's path, not just ones under the actor's home directory** — including auth and secret targets that legitimately live elsewhere. This has a real, documented consequence: a target that traverses a *system* symlink (a common Debian-family symlink from one system directory to another, or a merged-`/usr` layout) is rejected exactly like a symlinked path under home, with the resolved form of the target as the documented workaround. No real target has yet needed an exemption from this, and an ownership-based heuristic can't reliably separate a benign symlink from a hostile one, so no exemption mechanism was added speculatively.

**Two stable rejection codes, not a generic failure.** Every rejection under this guard originally surfaced as the same content-free `500` any other write failure produces. Rewritten to return a typed path error carrying one of two stable codes — one for "a path component is a symlink," one for everything else shape-related (empty/relative path, or a component that exists but isn't a directory) — answered as `422`, with the rejected file's own path in the body and never any content or an internal ancestor path. The broker parses this back into a matching typed error and logs both the code and the path explicitly (paths are configuration, safe to log; content stays secret-grade). No new wire fields were introduced: the body is still the same unstructured string `/bootstrap` has always returned for a rejection, just in a stable, parseable shape for this one class of error. A later hardening pass found the broker's own parser could be fooled by a path whose *content* happened to contain the delimiter text the parser searched for (e.g. a directory literally containing that phrase) — fixed by finding the end of the quoted path first (via Go's quoted-string-prefix parsing) and only then checking for the delimiter, rather than searching for the delimiter blind across the whole remainder.

**Log-line and error-quoting hardening.** A rejected-path log line initially named the path twice — once raw, once already-quoted inside the error text it also logged — so a path containing an embedded newline could split one log entry into two, forging what looks like a second, independent log line. Fixed by logging only the (already-quoted) error text. The same reasoning applied symmetrically on the broker side for the parsed error's own `Error()` method.

## Transport-limit signaling

The bootstrap handler originally bounded the request body with a plain limited reader, which truncates an over-limit body silently rather than signaling that the limit was actually hit — in practice this surfaced as an ambiguous JSON-decode `400` with no indication of the real cause. Switched to the standard library's request-body-size-limiting reader, which fails the read closed at the exact limit with a distinguishable error, now reported as a clean `413`.

## Privilege drop: substrate breaks assumptions written for Docker

Substrate always starts the actor process as **UID 0 with a minimal capability set** (a handful of baseline capabilities, no `CAP_SETUID`/`CAP_SETGID`). `sciontool init`'s privilege-drop logic long predates Substrate and was written against Docker's defaults, which grant a much larger baseline set. This mismatch surfaced as a sequence of increasingly specific live failures:

**1. `su` failed outright: no `CAP_SETUID`/`CAP_SETGID`.** The exec-as-user wrapper's `su -` call needs both to leave root. Fixed by explicitly granting both on the ActorTemplate's container security context — the *same* two capabilities Docker's own default set already includes, which is exactly why this defect is Substrate-specific rather than a general scion bug. These apply inside the sandbox the actor runs in, not the host; `su` itself still drops all of them for the process tree it execs into, so nothing scion-owned ever runs privileged as a result.

**2. Granting the capabilities alone didn't fix the drop — a second, independent gap.** Even with both capabilities present, the init code's own privilege-drop decision short-circuits to "stay at UID 0" whenever two environment variables it expects (conventionally set by every other runtime's own config-building path) are absent — and Substrate's bootstrap env-building path was entirely separate from the helper every other runtime funnels through, so it never set them. Fixed by setting both, unconditionally, to the actor image's own baked-in service-user UID/GID. Unlike Docker/Podman (where these normally mirror the *host's* own UID/GID for bind-mount permission parity) or the shared-filesystem backend (a stable, node-independent identity), Substrate's workspace is never bind-mounted from the broker's own filesystem at all, so there is no host identity to synchronize with — the image's own baked-in default is the only value that makes sense.

**3. Silent fallback to root is unacceptable here, but "failing" turned out to need three separate iterations to actually mean something.** The init code's existing behavior — quietly continuing as root when a drop can't happen — is correct and load-bearing for other runtimes (a legitimate rootless mode relies on it), but wrong for substrate: scion must never run the harness or an exec call as root there. Making this fail *closed* took three attempts to get right:
   - **First attempt:** a flag, set only by substrate-serve's own init-runner construction (deliberately not an environment variable a workload could set itself), that fails the in-process init call when the drop didn't happen. This stopped the harness from starting — but didn't fail anything visible: the in-process call returning non-zero didn't make PID 1 exit, the bootstrap HTTP response had already answered success before this code ever ran, and nothing reported the failure to the hub. The actor was left running, empty, reporting healthy — the exact silent-failure shape this change was meant to eliminate.
   - **Second attempt, and a discovered platform constraint:** a synchronous precondition check added *before* the bootstrap handler ever commits to a success response — re-verifying (cheaply, without performing any of it) the same three things that can make the underlying realignment silently produce nothing: the two capabilities effective, the service user resolvable, and the two environment variables present and parseable. When this fails, bootstrap answers non-2xx and never starts the init runner at all — reusing the broker's *existing* non-2xx-bootstrap failure handling (which already deletes the actor and fails the run) rather than inventing new plumbing. The original flag-based check stays as defense in depth. Separately, it was later confirmed that Substrate does **not** observe a PID-1 exit as a failure signal at all — the actor stays running and keeps holding its worker either way — so an earlier design that made PID 1 exit on any non-zero init result was reverted: the control server now deliberately **stays up** after a failed init, flips a health-endpoint state to a distinct "init-failed" value (still `200`, so the broker's health checking doesn't itself change shape, but a caller that knows to look can tell the difference), and relies on the init code's own *direct* report to the hub as the actual failure signal. The hub only shows an agent as errored if that direct report succeeds — this is not implied by the actor's own state, which stays "running."
   - **Third gap: a missing service user in the image was silently treated as a successful drop.** With both capabilities present but no service user actually present in the image, the drop logic still reported success as if it had happened, because its user-lookup failure was logged but not treated as fatal, and a subsequent shell substitution used to adjust the user's passwd entry exits successfully whether or not it actually matched anything. The harness ended up running as a raw numeric UID with no passwd entry at all. Fixed, gated on the same fail-closed flag so no other runtime's behavior changes: an unresolvable service user, a passwd-entry rewrite that didn't actually match a line, or a post-adjustment identity check that doesn't show the expected UID/GID, all now fail closed under the flag instead of only logging.

**4. Root itself is not all-powerful once its capability set is restricted — three more capabilities, found live, one at a time.** Once the drop was actually enforced, still-root init code doing routine root-phase work started failing:
   - `CAP_CHOWN` — the init code unconditionally chowns the log file, then the workspace and home tree, from root to the service user. Without this capability, chowning to an arbitrary different UID fails regardless of the caller's own UID once capabilities are restricted — the same "still UID 0 isn't still all-powerful" property that made the exec-user capabilities necessary in the first place.
   - **`/` itself came up too restrictive to even traverse into**, and **image-layer files under the home directory were observed owned by UID 0** even though runtime-created files were owned correctly (the exact upstream mechanism for the latter was never identified — only the symptom and its fix). Both are actor-startup-time conditions with a matching fixup: a new startup routine widens the root filesystem's mode only if it's more restrictive than needed (never narrows an already-wider mode — idempotent and quiet, logging only when it actually changes something) and re-chowns root-owned entries under the resolved home directory. It runs once at control-server startup — early enough to be captured in the golden snapshot, so a restored actor never has to redo the home-tree walk — and again, defensively, right before the privilege-drop precondition on every bootstrap, in case a pre-snapshot actor somehow reaches that path without having gone through startup. The precondition check itself gained matching traversability/ownership checks (every ancestor of the home and workspace directories must be searchable by the target UID/GID; the home directory itself must be owned by and writable by the target UID) computed from stat data alone, never by actually attempting the traversal.
   - **`CAP_DAC_OVERRIDE` — found live, and initially missed because a *different*, still-unfixed blocker was masking it.** An earlier attempt to add this capability, made before the rootfs fixup above existed, observed no effect and was left out — at that time `/` itself was still impassable, which blocked the actor before the interaction this capability actually fixes ever became reachable. Once the rootfs fixup landed and a live run got past `/`, the actual failure surfaced: `/healthz` reported "init failed" with the init log stopping immediately after a routine status line, no visible error at all. Root cause, two independent defects on the same path: (a) the startup fixup chowns the home directory to the service user at a restrictive mode *before* the still-root init code's own remaining root-phase writes into that same directory (staged secrets, agent-info, hooks) — without `DAC_OVERRIDE`, root is subject to the same permission check as any other non-owning UID against a directory it doesn't own, so every one of those writes failed; (b) independently, the log file itself gets chowned to the service user partway through that same root phase, so every root-phase write failure *after* that point — including the one that would have explained defect (a) — was being logged into a file root could no longer append to, and silently lost. Fixed by adding the capability; the ordering that let the log go silent is a standing sharp edge for any future root-phase write not covered by an existing capability, documented rather than restructured, since restructuring the ordering was explicitly out of scope for this fix.

The full required-capability list, its `CapEff` bit position, and a cited reason per entry live in one small, dependency-free package imported by both the code that grants the capabilities (the ActorTemplate builder) and the code that checks for them (the bootstrap precondition), specifically so the two can never drift apart — a capability present on one side but not the other is exactly the defect class this shared source of truth exists to prevent.

## The hermeticity incident: a test wrote this branch's own agent status to the real hub

A test exercising the privilege-drop failure path drove the *real* init code end to end. Two of that code's helper functions fall back to a real system user lookup, ignoring `$HOME`, whenever the process isn't running as UID 0 — and the development container this test ran in happens to have a real system user matching the name the code looks up. The real lookup succeeded, the test wrote a failure status to that real user's real home directory, something outside the test process (the container's own agent supervision) relayed that write to the real hub, and the hub put this branch's own development agent into an error phase and revoked its credentials — bouncing messages and eventually killing the very session doing this work, for roughly half an hour, and recurring once more while the mechanism was being isolated.

**Fix, two independent, both required per a binding rule that followed from this incident: no test may be able to reach a real hub or write real agent state, even when the ambient environment has real credentials and a matching real UID.**

- Every user-lookup call site in the affected package now goes through an injectable indirection (defaulting to the real function, so production behavior is unchanged) instead of calling the standard library directly.
- A package-wide test setup routine clears every hub/token/agent-identity environment variable, the two capability-drop-target variables, and points the injectable lookups at "not found" for the *entire* test binary — a single test's own environment-scoping only protects that one test, not any helper it calls into that resolves a real account independently of `$HOME` or the environment.

This was proven load-bearing, not assumed: deliberately removing just the lookup-stub override (leaving every other layer in place) and re-running reproduced the incident exactly — confirming this specific layer, not the environment-clearing, is what actually prevents it. It was reverted immediately afterward and the real, accidentally-modified file was hand-repaired to its correct state (a source-controlled fix for the gap itself — rather than a live re-run to merely demonstrate the gap — followed once a proof mechanism that didn't require touching a real account existed; see below).

**Three more hermeticity gaps, found by the same class of investigation:**
- A *different* test drove the real server-construction path and set some but not all of the environment this code path reads — specifically leaving the real `$HOME` unredirected. Under the exact mutation the test exists to catch, the failure-reporting code resolved a real home directory and wrote to a **different** agent's own container's real state file. Clearing hub/token env vars and disabling user lookups (the first incident's fix) does not, on its own, stop a still-real `$HOME` from being reachable by a completely different code path. Fixed by redirecting `$HOME` and related base-directory variables to one disposable, per-test-binary temporary directory for the whole test run, and by making the server-construction helper accept its dependencies as injected values so a wiring-level test can never reach the real ones regardless.
- Under randomized test ordering, an unrelated test category started failing with a process-reaping error once shuffled after this package's own tests: the control server's PID-1 zombie-reaper installs a process-wide signal handler that reaps *any* reapable child, including one a same-binary, later test's own subprocess call was still waiting on itself — a race between two different reaping mechanisms in the same process. Fixed by making the reaper installation an injectable, test-stubbable indirection defaulting to the real one, disabled for the whole test binary.
- A logging package's own lazy initialization defaulted to appending to this container's real, on-disk log file whenever nothing had explicitly set a path first — meaning any test that exercised the real init code without having done so first was silently appending real-looking lines to a real file. Folded into the same per-binary test setup.

**A second, independent defense was added afterward, since a single override that can be silently deleted (as this incident's own root cause was) is a standing single point of failure:** the *production* implementations of the affected lookup functions were changed to refuse to run at all under the test-framework's own "is this a test binary" signal, returning a fixed sentinel error instead of falling through to a real lookup — mirroring a guard this codebase already uses elsewhere for a structurally identical "must never reach a real external endpoint under test" property. The test-setup override above remains the primary, first-line defense (and is what a developer sees fail immediately, with a clear assertion, if they accidentally remove it); the new guard is what still catches the *removal* of that override, since a variable's default reverting to its production function no longer means a real lookup can actually happen under test. Verified with a live re-run of the exact original mutation (the override removed, in the real environment, with the new guard the only thing standing in the way): a hash of the real state file was confirmed byte-identical before and after — this is a demonstration that the guard holds, not the accepted proof itself; the accepted proof is a direct unit test that calls the production lookup function itself (bypassing the test-setup override entirely, exactly the shape of the original incident) and asserts it refuses, since this environment has no throwaway UID or namespace to run this specific mutation class in an actually-isolated sandbox.

**A goroutine leak, found as a side effect of proving the above under heavy repetition.** A large repeated-and-shuffled run of the affected test package (required to gain confidence in the reaper-race fix above) instead hung with tens of thousands of live goroutines: the control server's SIGTERM-handling goroutine never exits on return — harmless in the real, single-invocation binary, but a wiring-level test that calls the server-construction function directly leaked one goroutine per call, accumulating across a large repeated run until the process buckled. Fixed by stopping and closing the signal channel on every return path, with a dedicated regression test that calls the construction function many times and asserts the live-goroutine count stays flat.

## Exec-side CA-bundle environment passthrough

Once `egress_trust_bundle` (see the runtime/settings log) needed the actor's own processes to trust the MITM gateway's CA, a gap specific to the exec path surfaced: substrate-serve's exec handler always runs as root and switches to the target user via a login shell (`su -`), and a login shell discards essentially the whole inherited environment, keeping only a minimal login set. None of the CA-bundle variables survive it — a script invoked via exec that makes its own HTTPS call under the MITM gateway would fail even though the harness itself, launched a different way, trusts the gateway fine.

Fixed, in the substrate-specific copy of the exec-user wrapper only (not the shared helper every other runtime uses, since `-w`/whitelist-environment is a util-linux-specific flag and this whole mechanism only exists to counter Substrate's own environment-propagation shape): the wrapper now passes the login shell's environment-whitelist flag, naming only whichever CA-bundle variables are actually set, whenever at least one of them has a value — producing a byte-identical script and argument list to before on every plain install, since none of those variables is ever set there. The candidate variable names are read from the same shared, dependency-free list the ActorTemplate builder uses to set them in the first place, so the two sides cannot drift apart; a test on each side confirms they still agree. Building the whitelist argument in Go rather than shell was a deliberate choice: the wrapper already produces a fully-resolved argument list with no shell-side string processing to reuse, and a pure-Go list construction is trivially unit-testable (every combination of set/unset/empty-string-counts-as-unset) with no real shell or `su` needed — a confidence test that runs the generated script through a real shell with a stubbed `su` is included anyway, since it's cheap and closes the gap between "the Go string implies this" and "a real shell parses it this way."

This mechanism requires a login-shell implementation new enough to support the whitelist flag; the images this runtime targets already satisfy that requirement.
