# Project Log: Closing Verification Gaps in the Root Privilege-Drop Gate and Recursive Chown

**Date:** 2026-09-26
**Component:** `cmd/sciontool/commands/init.go`, `pkg/sciontool/supervisor`, `pkg/sciontool/dirfd`

See `2026-09-26-substrate-rootfs-op-symlink-hardening.md` for the fd-based tree-walk primitives and the fail-closed privilege-drop gate this entry hardens the verification of, and that entry's own "Hardening after independent review" section for the pattern this continues.

## What this closes

Substrate's fail-closed check — `sciontool init` must refuse to hand the harness off to a supervised child process unless a real, non-root UID *and* a real, non-root GID were both resolved — is implemented in exactly one place (`requirePrivilegeDropOrFail`) and threaded through exactly one call site in `RunInit`. Further scrutiny of that single call site found that nothing actually verified the call passed through the *real* resolved GID rather than some other value: a test double that stubbed the upstream user-resolution step could not distinguish "the real GID reached the gate" from "the UID was silently duplicated into the GID slot," "a hardcoded placeholder was substituted for it," or "the gate's own comparison only rejects a GID of exactly zero rather than any non-positive value." Any of those defects would have let a workload process that somehow obtained a non-root UID paired with a root or negative GID slip past the gate and have its child process launched with no credential drop applied at all, silently running as root.

A new test now drives `RunInit` end-to-end with the user-resolution step stubbed to return a small set of UID/GID pairs chosen specifically to distinguish each of those failure modes from correct behavior, and asserts the harness refuses to launch in every case. A second test independently confirms every one of the eight test-only substitution points in the user-setup path still defaults to the real function it exists to let tests replace — a substitution point silently becoming a permanent no-op would disable the underlying checks in production while leaving every existing test, which only ever reassigns it for the duration of its own run, still green.

A further gap in the same gate: the fail-closed check only ever ran against inputs where the user-resolution step reported a genuine privilege drop failure. It did not exercise the case where that step instead reports success but flags the result as not requiring a drop in the first place — a legitimate outcome on some runtimes, but on substrate a signal that must never be allowed to bypass the same refusal, since substrate's own privilege-drop contract has no equivalent legitimate "still root" outcome. Two new tests, one at the harness-launch gate and one at the supervisor's independent copy of the same check one layer below, now drive exactly that input and confirm both layers still refuse to start any downstream process — git clone, the sidecar services, and the supervised child alike — rather than treating it as an exemption.

The supervisor's own independent copy of this same fail-closed decision — one layer below `RunInit`, guarding against a future caller that might construct its child-process configuration directly rather than going through `RunInit`'s gate — previously only had test coverage for a UID and GID that were both zero. It is now exercised for every UID/GID combination its enforced-mode counterpart already covers, including a non-root UID paired with a root GID, since that specific pairing is a real input on non-Substrate runtimes today and must keep running the child without a credential rather than erroring once fail-closed enforcement is off for that runtime.

The recursive, fd-based ownership-chown primitive introduced to close the broader class of root-filesystem TOCTOU exposures already proved every one of its per-entry chown and delete operations acts on a held file descriptor rather than a re-resolved path — except for the operation on the root directory itself, which had no test proving the same property because the primitive offered no way to inject a race at that specific point. It turns out one already existed: the primitive's own caller-supplied filter callback runs at exactly the moment between root being opened and root being chowned, so a test can use it to rename root's own directory entry right there, with no change to the primitive itself. A new test does exactly that and confirms the chown still lands on the original directory via its held descriptor, closing the one entry point in this primitive that previously had no direct proof against this exposure.

## A byproduct: a static-analysis finding on already-correct logic

Independent scrutiny also flagged that the gate's clamp — expressed as a negated conjunction (refuse unless *both* UID and GID are positive) — is logically identical to a disjunction of the negated terms (refuse if *either* is non-positive), and static analysis prefers the latter form. The rewrite is a pure identity for every possible input, including negative UIDs and GIDs, and does not change behavior; it exists purely so the codebase's own linting stays clean going forward. The doc comment on the gate now also states plainly why a non-root UID can never actually be paired with a root GID in production today: the Substrate actor bootstrap path hardcodes the target GID unconditionally, independent of whatever UID gets resolved. The clamp does not rely on that staying true — it exists specifically so a future change to that resolution path fails closed rather than silently reintroducing this exposure.
