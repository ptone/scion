# Project Log: In-Cluster Broker Deployment Manifest

**Date:** 2026-09-25
**Component:** `deploy/substrate/broker.yaml`, `deploy/substrate/README.md`

See `deploy/substrate/README.md` for the operational contract as it stands today (placeholders, apply order, verification commands, known limitations) and `.design/kubernetes/substrate-runtime.md` §1 for why an in-cluster broker is required at all. This entry records the manifest's structural decisions and the live-deploy defects found and fixed while standing it up, rather than restating the README's own content.

## Manifest shape and scope

A single plain manifest (Namespace, ServiceAccount, RBAC, ConfigMap, Deployment, NetworkPolicy — one file, no Helm chart), matching this repo's existing precedent for a minimal, non-templated deployment fixture rather than the polished chart Phase 2 will need. The broker is the same `scion` binary the hub image already builds, run with broker-only flags (`--enable-runtime-broker`, no `--enable-hub`) rather than a separate image or Dockerfile.

**RBAC is scoped to exactly three needs, each pinned as narrowly as the API allows:**
- `create` on `serviceaccounts/token`, `resourceNames`-pinned to the broker's own ServiceAccount — the dialer mints a token only for itself, never for any other identity, and the RBAC reflects that rather than granting the broader unscoped permission.
- `get` on `certificates.k8s.io/clustertrustbundles` (necessarily a `ClusterRole`, since the resource is cluster-scoped, not namespaced), `resourceNames`-pinned to the one bundle name the runtime is actually configured to read. An early version of this granted unscoped read access to *every* `ClusterTrustBundle` in the cluster — every signer, every tenant — when only one specific name is ever needed; narrowed once flagged.
- `get` on `pods`/`pods/log` in the worker namespace, for `GetLogs`, as a `Role`/`RoleBinding` pair whose subject reference crosses from the broker's namespace into the worker namespace — the two are almost certainly different namespaces on a real cluster, and the manifest treats that as the expected case rather than an edge case.

**No secret values live in the manifest at all.** The broker authenticates to the hub via a Secret created out-of-band from a local `register` step, never pasted into a committed file; the manifest's own comment documents the shape of that Secret (as a non-live, commented-out reference) without ever instantiating one. The settings ConfigMap deliberately includes the broker's non-secret identity fields (a stable UUID, a URL) but not the older, secret single-shared-token auth field from the same settings struct — flagged explicitly in a comment so a future editor doesn't fold the whole settings block in by analogy and accidentally commit a credential.

## Why there is no hand-written NetworkPolicy for the worker/actor side

The Phase 1 bootstrap-nonce fallback (`.design/kubernetes/substrate-runtime.md` §5.2) depends on the router being the *only* reachable path to an actor's control server — otherwise any pod that can reach a worker pod's IP directly, bypassing the router entirely, can also bypass the single-shot bootstrap check that fallback relies on. This manifest supplies half of that guarantee (a NetworkPolicy restricting the router's own ingress to the broker's namespace); the other half — restricting ingress to the *worker* pods themselves — is deliberately **not** duplicated here, for a reason stronger than "it would be redundant": Substrate's own worker-pool controller already creates a NetworkPolicy per WorkerPool that is *more precise* than any hand-written equivalent could reasonably be (an AND of a specific namespace and a specific pod label, not "anyone in that namespace"), and NetworkPolicies that target the same pods are OR'd together, not ANDed — so a broader, hand-written policy alongside Substrate's own tighter one would not add a second layer of protection; it would **silently widen** access back to whatever the broader policy allows, undoing the precision of the one that already exists. This was confirmed against the actual controller source before making the call, not assumed from documentation.

An earlier version of this manifest did carry a hand-written worker-namespace policy, added when the OR-semantics interaction above hadn't yet been checked. It went through one correction first (a first attempt scoped it to the wrong port — Substrate's own worker pod exposes its actor-tunnel ingress on a different port than the actor's own control server, which the worker pod's network namespace doesn't expose at the pod-network level at all; a NetworkPolicy naming the wrong port would have simultaneously broken real traffic and protected nothing) before being removed outright once the OR-semantics interaction with Substrate's own generated policy was understood. The manifest's own comment records both the technical reasoning and a pointer to the exact upstream function that generates the real policy, specifically so a future reader doesn't mistake the absence of a worker-namespace policy here for an oversight.

## `active_profile`: the broker's own default-runtime resolution needs an explicit anchor

**Symptom, from the first live deploy:** every heartbeat logged a `docker ps failed` warning.

**Root cause:** the broker's heartbeat loop lists agents through its *primary* manager — resolved once, at startup, via the runtime factory's empty-profile-name path — which is a separate resolution from the auxiliary managers substrate profiles live in. An empty profile name falls back to the settings' own active-profile field; the manifest defined `runtimes`/`profiles` entries making substrate *resolvable*, but never set that active-profile field, so the fallback had nothing to resolve to, resolution failed, and the factory's own last-resort fallback landed on Linux auto-detection — which picks `docker` when nothing else signals a better choice. The broker's primary manager was therefore a Docker runtime shelling out to a binary that was never going to exist in this image.

Fixed by setting the active-profile field explicitly to the substrate profile name in the ConfigMap. This is not a workaround: the `runtimes`/`profiles` entries alone only make a profile *resolvable* when asked for by name; the active-profile field is what makes it the one actually used when nothing more specific is requested — exactly what the heartbeat's own empty-profile-name resolution does on every tick.

## Broker API binding and why `0.0.0.0` is safe here

**Symptom:** the Deployment's own readiness and liveness probes failed with connection-refused.

**Root cause:** a standalone broker with no explicit host flag binds to loopback only, by design — a safety net so a *freshly* started broker with no HMAC keys loaded yet can still be reached locally to register before those keys exist. Kubelet's HTTP probes connect to the pod's own IP, not to loopback inside the container's network namespace, so the default safety net actively broke the probes it wasn't designed to interact with at all.

Fixed by passing an explicit host flag, which both opts out of the loopback-only default and (confirmed by reading the flag-handling code directly, not assumed) has no other effect in this deployment's configuration, since every other setting that flag also touches is gated behind flags this deployment never passes.

**This is safe specifically because of how this broker's HMAC auth is configured, not despite it:** strict HMAC auth mode is the unconditional default here (no flag or setting in this deployment turns it off), and — more importantly — the broker refuses to even start its HTTP listener on a non-loopback host unless valid HMAC keys are already loaded from the credentials Secret. It does not fall open to an unauthenticated non-loopback listener under any configuration this manifest can produce; if the credentials Secret is ever missing when the pod starts, the broker now fails closed (crash/restart) rather than serving unauthenticated, which is a useful side effect of the same fail-closed startup check, not a separate feature. A narrower ingress policy scoping the broker's own API port to kubelet-only traffic was assessed as worthwhile future hardening but not added: there is no NetworkPolicy peer expression for "the kubelet" or "the node this pod runs on" as such, and expressing it via an IP block would need cluster-specific node-CIDR information this manifest doesn't have.

## Settings location: the broker's identity is not where a naive guess would put it

An early draft placed the broker's hub-facing identity (its ID and the hub endpoint) under an invented, plausible-looking top-level settings key. Checking the actual settings struct directly, rather than trusting the plausible guess, turned up the real, current location — nested under the server/broker settings block — confirmed as the current, non-deprecated location by the settings loader's own legacy-key migration, which explicitly maps an older flat key to this nested one. This also surfaced a related risk worth flagging on its own: the *same* struct that holds the broker's non-secret identity also holds an older, secret single-shared-token auth field — an easy mistake would be to fold that whole block into the ConfigMap by analogy with the identity fields next to it. The manifest includes only the non-secret fields and documents explicitly, in-line, why the secret one is deliberately absent.

## The worker-namespace label match: two different label sets that look similar

The `worker_selector` setting is matched against a WorkerPool custom resource's *own* `metadata.labels` — not the label Substrate's own controller separately stamps onto the worker *pods* it generates for k8s-native pod selection (NetworkPolicy `podSelector`s and similar). These are two different label sets, on two different kinds of objects, that are easy to conflate because they often share syntactically similar-looking values on a given cluster. Getting this wrong does not fail at apply time — the manifest renders and applies successfully — it fails at actor-creation time, with an error about no free workers matching, even when a pool with real capacity exists. The README documents the exact `kubectl` command to read the correct value directly off the WorkerPool object itself, rather than off the pods it manages, specifically because inspecting the pods produces a plausible-looking but wrong answer.

## NetworkPolicy enforcement is a precondition, not a property of the object existing

`kubectl apply` succeeding for a NetworkPolicy object says nothing about whether anything on the cluster actually enforces it — a cluster without an enforcing CNI addon accepts the object and enforces none of it, silently. This matters enough to verify with real traffic, not just object presence, and the README's verification steps do exactly that (a probe from outside the expected scope must be refused; a probe from inside must connect). A related, non-obvious operational fact worth calling out here since it shaped how those verification steps are written: enabling NetworkPolicy enforcement on a cluster that already has actors running is not a same-day, apply-and-go change — it requires labeling any pre-existing nodes so the enforcement daemonset actually schedules onto them, rolling-restarting every pod that must become subject to enforcement (explicitly including the router pod itself, not just the workers — a pod created before enforcement was enabled keeps its original network setup and gets no enforcement regardless of what NetworkPolicy objects exist, and an unrestarted router pod leaves the router-ingress policy completely unenforced while `kubectl get networkpolicy` still shows it as applied), and rebuilding any golden actor-template snapshot taken before enforcement was live, since a snapshotted network-namespace state can be incompatible with the enforcement mechanism's own network plumbing.

A related documentation trap worth recording: whether NetworkPolicy enforcement is active at all cannot be determined from a single, commonly-checked cluster field — that field only ever reflects one specific enforcement backend, and checking it alone gives a false "enforcement is off" reading on a cluster enforcing via the other supported backend. Both signals need to be checked together.
