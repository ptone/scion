# Project Log: Closing Root Path-Based Filesystem Operations on Substrate

**Date:** 2026-09-26
**Component:** `pkg/sciontool/dirfd`, `pkg/sciontool/services`, `pkg/sciontool/supervisor`, `cmd/sciontool/commands/init.go`

See `pkg/sciontool/dirfd`'s package doc comment for the general shape of the class this closes, and the hub token/env-file hardening landed just before this change for the pattern this work extends.

## The class

On Substrate, root runs for the whole life of `sciontool init`/`substrate-serve`, while the workload user owns `$HOME` and `$HOME/.scion` outright. Sidecar services and pre-start hooks run as that workload user, sometimes concurrently with root's own work, sometimes strictly before it but still able to leave files or symlinks behind for root to find later. Any root filesystem operation that resolves a path the workload user can influence — and either follows a symlink at the final component, or re-resolves an intermediate path component on every step of a walk — is exploitable: a workload process swaps a real directory for a symlink to an attacker-chosen target, and root's next open/chown/delete lands there instead.

A prior pass closed two known instances of this class (the hub agent-token file and the generated shell-env file) by resolving each path exactly once, into an open directory file descriptor, and performing every subsequent step — create, read, chown — relative to that descriptor rather than by re-resolving the path string. A systematic sweep of the rest of the substrate init/serve/services/supervisor surface, done after that pass landed, found the same shape recurring in five more places. This change closes all five, reusing the same fd-based primitives rather than inventing new ones, and adds two new shared helpers to the primitives package for the two shapes (a chown that recurses through a whole tree, and a delete that recurses through a whole tree) that didn't previously have a fd-based implementation to reuse.

## The two new shared primitives

`dirfd.ChownTreeNoFollow` and `dirfd.RemoveContentsNoFollow` both walk a directory tree by holding an open, no-follow file descriptor for every directory they are currently inside, and opening each subdirectory relative to its parent's held descriptor rather than by joining path strings. Every chown is `fchownat` with `AT_SYMLINK_NOFOLLOW` issued against the currently-held parent descriptor; every delete is `unlinkat` (with `AT_REMOVEDIR` for emptied subdirectories) against the same. Because a directory's own file descriptor is bound to the inode it was opened against — not to whatever name currently refers to that inode in its parent — nothing that happens to a directory's entry in its parent after the walk has already opened and descended into it can redirect any operation still in flight beneath it. This is a structural property, not a race the fix merely tends to win: a directory renamed away and replaced with a symlink to an attacker's directory, at any point after the walk has opened it, has no effect on the operations the walk goes on to perform inside the fd it's still holding.

Both primitives were proven against exactly this scenario in their own tests: a directory the walk has already opened is renamed away and replaced with a symlink to a victim directory, injected deterministically through a test-only hook fired at the precise point production code has no equivalent of (immediately after opening the subdirectory, before recursing into it) — the same style of deterministic race injection already used for the shell-env file's directory-chown fix. The victim is proven untouched, and the walk is proven to keep operating correctly on the original, now-renamed directory via the descriptor it already held. A hand-rolled reimplementation of the historical path-based approach (walk, then chown/delete by re-joined path string) was run against the identical scenario and confirmed vulnerable — the victim was touched — establishing that the test actually distinguishes the fixed shape from the broken one, not just that both happen to leave a differently-named victim alone.

## Where the five instances were and how each was closed

**Service log files.** Every sidecar service's stdout/stderr/lifecycle log was opened with a plain `os.OpenFile` (no `O_NOFOLLOW`) and then chowned by path, one service at a time, interleaved with starting that service and waiting for its readiness check — a wide window in which an already-running service (itself running as the workload user) could symlink-swap a not-yet-opened log path before root reached it. The fix opens every service's logs (fd-based, `O_NOFOLLOW`, fstat-verified as a single-link regular file) and chowns them all before starting any service at all, removing the window by construction rather than narrowing it. This ordering change is observably identical to the previous behavior in the success path — every log still ends up opened, chowned, and used exactly as before — so it applies unconditionally, on every runtime, not just Substrate.

**The supervisor's home-directory chown.** Immediately before exec'ing the child process, the supervisor recursively chowned the entire home directory to the workload user via a plain directory walk and per-entry `Lchown`, while sidecar services and any process a pre-start hook spawned could already be alive. `Lchown` itself never follows the final component of the path it's given, but it does re-resolve every component *above* the final one on every single call — so a workload process that swaps a directory the walk has already visited for a symlink can redirect a later call in that same walk outside the tree entirely. This now delegates to the shared no-follow tree-chown primitive.

**Restoring ownership after pre-start hooks.** The same walk-and-`Lchown` shape existed a second time, independently, in the step that fixes up root-owned files a pre-start hook may have left behind under the workspace or home directory — hooks themselves run as the workload user, so by the time this step runs, workload-owned processes may already exist. Originally, dropping this step in favor of an existing later fixup step (documented as running before any workload process exists) was considered, but that documented precondition turned out not to hold: the later step runs strictly after these hooks, not before them. Since that "safe fallback" premise didn't hold, and the alternative of proving the later step covers an identical path set at a provably-later point was not attempted (hardening being the more conservative and simpler option once the fallback premise failed), this step was hardened in place, on the same shared primitive as the supervisor's chown, rather than dropped.
This step, unlike the supervisor's own chown, runs on every runtime whenever the calling process is root — not only Substrate — because it fixes up provisioner output for the non-root broker generally. Only Substrate has an actual, less-privileged workload user and an ancestor-path-symlink threat model to defend against, and only there does the fd-relative walk's refusal of a symlinked ancestor path have a security justification; a legitimate non-Substrate setup can symlink an ancestor of the workspace or home directory (e.g. from a bind-mounted host path) with no privilege boundary at stake. So this one call site keeps its historical path-based implementation, unchanged, on every runtime except Substrate, and only switches to the fd-relative primitive when Substrate's own privilege-drop requirement is in effect. A missing root directory is a silent no-op on both branches, matching the historical contract exactly.

**A Claude Code compatibility workaround.** A directory under the workload's home is pre-created and made read-only as a workaround for a Claude Code quirk, using a plain create-if-missing-then-chmod sequence that follows a symlink if one is already sitting at that path — deterministically exploitable, no timing race required, since the exploit only needs the symlink to exist before this code runs, not to be swapped in during it. This is now resolved with the no-follow directory primitive already used by the shell-env fix, and the resulting descriptor is chmod'd directly rather than by path. Because a legitimate non-Substrate setup could plausibly symlink or bind-mount this same directory from a host path, the historical behavior is left completely unchanged on every runtime except Substrate; on Substrate, a refusal is logged and the step is skipped rather than treated as fatal, so a planted symlink cannot be used to prevent the workload from starting at all.

**Clearing stale gcloud configuration.** When the emulated metadata server is enabled, stale gcloud configuration state is cleared out (preserving one file that may be a bind-mounted credential) so gcloud re-discovers the emulated server on its next run. The historical implementation read the directory and deleted each entry by re-joining the directory's own path with the entry's name — if the directory itself were a symlink, every deletion would resolve through it, and this step runs after sidecar services have already started, so both the deterministic "already a symlink" case and a mid-walk swap of a subdirectory are both live concerns. The fix opens the directory once, no-follow, and empties it via the new no-follow recursive delete primitive, so nothing is ever deleted by a re-resolved path. As with the Claude Code workaround, non-Substrate runtimes keep the exact historical behavior; Substrate logs and skips a refusal rather than failing the workload's startup.

## What stays unconditional versus what stays runtime-gated

The service-log reordering, the underlying fd-handling it and the supervisor's chown rely on, and both new tree-walk primitives' core no-follow mechanics are correctness fixes with no legitimate case that depends on the old, unsafe behavior, so they apply on every runtime. Three things are different, and are threaded through the same flag that already distinguishes Substrate's mandatory-privilege-drop runtime from every other one:

- The Claude Code workaround and the gcloud cleanup: a legitimate non-Substrate deployment can intentionally symlink or bind-mount the exact directories these two operate on (a host-mounted gcloud config, a bind-mounted `.claude` directory), and refusing that symlink outright would break a working, non-Substrate setup for no security benefit.
- The pre-start-hooks ownership fixup's no-follow strictness (described above): its path-based implementation stays the historical, non-substrate default; only Substrate gets the fd-relative walk.
- A new hard-link guard in the tree-chown primitive (below): a workload can pre-plant a hard link to a file it does not own, and a tree-wide chown that didn't check this could be tricked into handing an unrelated file to the workload. This is new, security-motivated behavior with no compatibility concern on Substrate, but a legitimately hard-linked file under a non-Substrate container's home directory must keep working, so the guard itself is gated even on the two call sites (the service-log open, and the supervisor's chown) whose surrounding fd-handling is otherwise unconditional.

The service-log reordering and the pre-start-hooks fixup's path-based branch do carry one small, deliberate behavior change even on non-Substrate runtimes, called out explicitly rather than left implicit: a symlinked ancestor component of `$HOME` (for the service-log directories) is no longer silently created/followed the way `os.MkdirAll` would, and a missing `$HOME` is no longer auto-created by the service manager. Both are accepted as having no legitimate dependent case — nothing in this codebase relies on `$HOME` itself being absent at this point, or on an ancestor of it being symlinked out from under the fixed, well-known `.scion/services/logs` layout.

## Hardening after independent review

Independent review of the initial version of this change surfaced several further points, addressed in the same unit:

- **Silent per-entry failures.** The tree-chown and tree-delete primitives originally discarded per-entry failures (a chown or a delete that failed for one entry) without any way for a caller to observe them, even though the historical implementations they replaced always logged such failures. Both primitives now accept an optional callback invoked with the failing entry's bare name (never a full path, and never file content) for every per-entry problem — a failed chown, a hard-link-guard skip, or a depth-cap cutoff — and every call site wires it back to the same logging the historical implementation did.
- **A stat-then-act gap on the leaf name.** The tree-chown primitive's first version still resolved each entry's ownership decision and its chown through two separate name lookups (an `fstatat` by name, then a later `fchownat` by the same name), leaving a narrow window for the entry's name to be swapped between the two. It now resolves every entry to a file descriptor exactly once — `openat(O_DIRECTORY|O_NOFOLLOW)` for a directory, `openat(O_PATH|O_NOFOLLOW)` otherwise — and both the ownership check and the chown itself (`fchownat(fd, "", ..., AT_EMPTY_PATH)`) happen against that one descriptor, closing the gap entirely rather than narrowing it. This is behavior-preserving and applies unconditionally, on every runtime.
- **Hard-link guard.** Neither the historical implementations nor the first version of the shared primitive checked whether a regular file being chowned had more than one hard link. Hard-linking a file only requires write access to the directory the link is created in, not ownership of the link's target, so a workload process can pre-plant a hard link to an unrelated (possibly root-owned) file and have a tree-wide chown hand that file to itself. The primitive now skips (and reports via the callback above) any regular file with more than one link when this guard is enabled; directories, which legitimately have more than one link from their own subdirectories, are never subject to it. As described above, this is new, security-motivated behavior, so it is enabled only where Substrate's privilege-drop requirement is in effect, on both call sites that use the shared primitive unconditionally otherwise.
- **Unbounded recursion depth.** Both primitives recurse once per level of directory nesting and hold one open file descriptor per level for the duration of that level's work. A pathologically deep hostile directory tree could in principle exhaust the process's file descriptor limit partway through a walk. Both primitives now cap recursion depth, reporting the cutoff through the same per-entry callback, well beyond any depth a legitimate tree under `$HOME`, `/workspace`, or a gcloud config directory is expected to reach.
- **Service startup partial-failure semantics.** The service manager's first version made log-file opening all-or-nothing across every sidecar service: if any one service's log path could not be opened (for example, because a symlink had been planted there), no service started at all. On Substrate this handed a workload process a denial-of-service lever against every sidecar merely by planting one symlink, which contradicts this unit's own principle — applied to the Claude Code workaround and the gcloud cleanup — that a planted symlink must not be able to stop the workload from starting. The manager now drops only the one service whose logs failed to open, logs it, and still starts every other service, including ones later in the list; log file descriptors for a dropped service, or for any service that never gets a chance to start because an earlier one's start failed, are always closed before the call returns rather than leaked.

## A second content-trust axis: root reading, and root building paths from, workload-writable content

Everything above defends against a symlink swapped into a path root resolves. A separate, later review pass identified a different axis of the same underlying class: root also *reads the content* of a workload-writable file to decide what to do, and *builds new paths out of workload-supplied strings* — neither of which a no-follow openat chain defends against, because no symlink is involved at all.

**The sidecar-services config file's content.** Root reads the sidecar-services YAML file to decide which processes to start and how, after pre-start hooks (which run as the workload user, who owns the containing directory outright) have already run — so the workload can simply overwrite the file in place, no symlink needed. This is read via the same no-follow-plus-regular-file-check pattern as the rest of this unit, gated the same way (unconditional path-based read on non-Substrate; no-follow, single-link-regular-file-checked read on Substrate, refusing a symlinked config file without aborting startup). That closes the symlink instance of this file, but not the deeper question: does the *content* the workload writes to it grant any privilege it didn't already have?

Tracing every field the parsed content can set through to the process it produces answers that: the file can name a command and environment variables, but the identity that command runs as is never read from the file at all. The service manager takes a single uid/gid pair for the *entire batch* of services, supplied by the caller — which is the same drop target the whole init process already enforces before this file is ever reached (a fail-closed check earlier in startup refuses to proceed on Substrate at all unless a non-root drop target was actually resolved). So a rewritten config file can make root start additional processes, but only ever as the workload's own already-held identity — no uid, gid, or capability the workload does not already have as itself. That is why the symlink fix above is sufficient for this file without any additional clamp: the content-trust exposure the symlink fix leaves open has no privilege to escalate into.

**A workload-chosen name used to build a path.** The same config file's per-service name field is concatenated directly onto fixed suffixes to build each service's log file path, then handed to an openat call that does not parse or split its argument on path separators — it resolves whatever string it is given, one component at a time, exactly as the kernel would resolve any other path. A no-follow flag stops that resolution from *following a symlink* at the final component; it does nothing to stop the *string itself* from containing `..` or embedded separators that walk the resolution somewhere else entirely. A workload-chosen name was therefore capable of directing root's own file-create-and-take-ownership operation to an arbitrary path outside the intended log directory — the same "root turns workload-writable content into a privileged filesystem action" shape as the file-content case above, just on the path-construction axis instead of the file-read axis, and with a real (not merely theoretical) escalation available since a create-and-chown primitive lands on an attacker-chosen target.

The fix validates every service name against the shape a path component is allowed to have — rejecting an empty name, `.`, `..`, an embedded separator, an embedded NUL byte, or an implausibly long name — before anything downstream ever concatenates it into a path. This has no compatibility cost on any runtime (a real service name is a short identifier; nothing legitimate is rejected), so it is enforced unconditionally rather than gated, at two points: once, authoritatively, immediately after the config file is parsed and before any consumer of the name exists; and again, defensively, at the point the log paths are actually built, so a future or different caller of that lower-level code cannot reintroduce the gap by skipping the first check. An invalid name drops only that one entry — logged with the name itself bounded in length and escaped before it ever reaches a log line, since the name is exactly the untrusted input in question — rather than refusing to start every other, valid service in the same file.

## Test coverage: proving the fixes, not just the code

A recurring lesson across this unit's own review cycle is that a structurally correct fix and a regression test that actually depends on it are two different claims. Several of the fixes above shipped, correctly, before a test existed that would fail if they were reverted — including the single-resolve fd fix itself, the no-follow flag on the delete walk's subdirectory open, the fd-based chmod in the Claude Code workaround, the hard-link guard at the pre-start-hooks-fixup call site, the fd-cleanup paths in the service manager's partial-failure handling, and the runtime-flag threading from the top of the init sequence down to every gated call site. Each of those now has a dedicated test built around the same technique used throughout this unit — a deterministic, test-only hook fired at the exact window a real race would need, or a real `/proc/self/fd` count where file-descriptor accounting is the property at stake — and each was confirmed, by temporarily reverting the corresponding fix and re-running the affected test, to fail against the reverted shape and pass against the shipped one. A previously-untestable call site (reaching an enforced, privilege-drop-required code path from a non-root test process at all) needed one small new seam to become reachable; every other gap needed a test only, no production behavior change.

## Verification

Every new and touched code path was exercised at three levels: the shared primitives directly (including the deterministic mid-walk swap proofs, dedicated tests for the hard-link guard, the depth cap, per-entry error reporting, and the single-resolve leaf/directory fd fix), each call site individually (proving the site correctly wires its own decision logic — which entries qualify for a chown, which file is preserved from deletion, which runtime flag it reads — onto the shared primitive), and the existing test suites for every touched package, which all continue to pass unchanged. Non-Substrate behavior for every runtime-gated site was proven byte-identical to the pre-existing implementation, including the legitimate symlinked-directory and hard-linked-file cases.

**Correction (round 4):** the previous paragraph's claim that "every regression test named above ... was confirmed, by hand, to fail against the pre-fix (or reverted-fix) shape" was **not true** for two of them, as two independent round-3 reviewers found and round-4 confirmed by actually running the mutation rather than reasoning about it. `TestOpenLogNoFollow_RefusesFifoWithoutBlocking` ("L1") raced an unsynchronized background goroutine against the FIFO open under test, so the write side almost always won and the test exercised incidental `ENXIO` rather than the `S_IFREG` check it claimed to guard — it passed identically whether or not that check existed. The onErr-reporting tests for the chown-walk's `O_PATH` openat site and the remove-walk's `Fstatat` site ("L3b"/"L3e") simply didn't exist yet; nothing guarded those two per-entry error paths at all. Round 4 fixed the first by attaching the FIFO reader synchronously (a non-blocking read-open of a FIFO never races, so the S_IFREG check is what the test actually exercises) and added the two missing tests, exercised with a real `chmod 0600` EACCES trigger rather than fault injection. All three are now confirmed below with pasted before/after evidence, not by inspection.

## Round 4: closing the test-coverage gaps, and a mechanically-verified mutation kit

Round 4's brief was narrower than the rounds before it: the *product code* reviewed in round 3 had no defect, but several of its regression tests were vacuous — they would keep passing even if the fix they claimed to guard were reverted, for two different reasons: a ctime "before" snapshot taken before a `rename(2)` that itself bumps ctime (so the assertion was true regardless of whether a chown ran), and the L1 race described above. Two independent round-3 reviewers caught this by actually reverting the code and re-running the tests; round 4's process mandate was to do the same for every test touched, and paste the evidence rather than assert it.

**What changed:**
- `TestChownTreeNoFollow_LeafSwapAfterResolveDoesNotRedirectChown` and `TestChownTreeNoFollow_DirEntrySwapAfterFstatDoesNotRedirectChown`: re-snapshot the "before" ctime immediately *after* the hook's `os.Rename`, not before, closing the vacuous-baseline gap.
- Added `TestChownTreeNoFollow_DirEntrySwapToHardlinkedFileDoesNotRedirectChown`: the same swap-after-resolve proof, but swapping in a hard link to a regular file instead of a symlink, with the hard-link guard enabled — proving the fd-based chown is immune to a vector that bypasses both the leaf-only hard-link guard and the `shouldChown` decision simultaneously.
- `TestOpenLogNoFollow_RefusesFifoWithoutBlocking`: rewritten to attach the FIFO reader synchronously before the open under test, removing the race; now asserts on the actual `"not a regular file"` error text.
- Added `TestChownTreeNoFollow_ReportsPerEntryOpenFailureViaOnErr` and `TestRemoveContentsNoFollow_ReportsPerEntryStatFailureViaOnErr`, guarding the previously-untested `onErr` sites for the chown walk's `O_PATH` openat and the remove walk's `Fstatat`, using a real `chmod 0600` (non-root EACCES) rather than a fault-injection hook.
- A previously-undiscovered High-severity path-traversal issue found along the way: a sidecar service's `Name` field was concatenated unsanitized into a log-file path, so `../../../etc/cron.d/x`-style names could direct root's create-and-chown outside the intended log directory. Closed with `services.ValidateServiceName` (rejects empty, `.`, `..`, an embedded separator, NUL, control characters, and over-length names) enforced at two points — authoritatively at config-parse time, defensively again in `Manager.Start` — plus `services.SafeNameForLog` for bounded, quoted logging of a rejected name. The broader Name charset allowlist beyond control-character rejection was explicitly deferred to a follow-up (lead decision), not implemented in round 4.
- `readServicesYAML`'s enforced-mode read gained a 1 MiB cap (`servicesYAMLMaxBytes`), refusing rather than reading past it.
- `runSetupHostUser`'s `RequirePrivilegeDrop` flag threading is now directly asserted in `TestRunInit_ThreadsRequirePrivilegeDropToEveryGatedCallSite` (previously the seam existed but the test didn't check the flag it received).
- `validateServiceSpecs`' parse-time gate call site is now guarded by `TestRunInit_ThreadsRequirePrivilegeDropToEveryGatedCallSite`'s companion assertion that an invalid entry is dropped while every other valid entry, regardless of position, is kept.
- Doc-comment nits: `onErr`'s doc comments on both tree primitives now mention listing failures (reported as `"."`) and non-`ENOENT` open/stat failures; two stale references to `validateServiceName` corrected to `services.ValidateServiceName`; "keeping every other spec, valid or not" corrected to "every other valid spec, regardless of position."
- **Declined (round 4, accepted by lead):** a `gid == 0` defence-in-depth clamp, and `onErr` coverage for the walks' `Readdirnames` and post-open `Fstat` sites, were both left as documented declines. Both walks are already fail-safe on these paths — a `Readdirnames` failure or a post-open `Fstat` failure simply causes that subtree to be walked as empty (no entries touched, nothing chowned or deleted) rather than escalating into an unintended action — so the missing observability is a logging gap, not a security gap, and adding it was judged not worth the additional test surface this round.

### Mechanically-verified mutation kit

To make round 4's mutation claims independently reproducible (rather than asserted, as the two prior rounds' claims were and were found wanting), a mutation kit was built on the task scratchpad — **not committed to this repository** — at `/scion-volumes/scratchpad/projects/substrate-integration/mutations/rootfsops/`: one authentic git-diff patch per named mutation (37 in total, covering every mutation ID enumerated across rounds 2 through 4, including this round's L1 S_IFREG check, all four Part C checks — Nlink, S_IFREG, O_NONBLOCK, and the ancestor no-follow walk — `runSetupHostUser`'s flag, the M4b hardlinked-file swap variant, and the L3 `openat`/`Fstatat` onErr sites), plus a bash runner (`run_mutations.sh`) that creates one detached git worktree at the repo's HEAD, applies each patch in turn, runs only that mutation's named test(s) with `-count=1` under a 30s (60s for the one race-sensitive test, run `-count=20`) timeout, records the result, reverts, and moves to the next — exiting non-zero if any mutation survives (its test still passes under the patch). The FIFO-based L1 test is run 20 times per the addendum's requirement for race-dependent tests; the one mutation whose expected symptom is a hang (`PartC-ononblock-removed`, which drops `O_NONBLOCK` from the enforced YAML read) is judged caught by the test's own bounded internal timeout firing, not by the runner hanging.

The full kit was run end-to-end against HEAD `5fb8d330f9197ae52cc8ac7339195427614fd822`: **37/37 mutations caught, 0 survived, runner exit code 0.** (One authoring mistake was caught and fixed during this process: the `PartC-ancestor-nofollow-removed` manifest row initially named the wrong package for its test, which made the runner report a false survival; correcting the package field to `cmd/sciontool/commands` and re-running confirmed the mutation is in fact caught.) The full runner output is pasted in the round-4 completion report to the dispatching agent.
