## R9(a): teaching the fd-anchored walk to follow a symlink it can prove is safe

The starting bug was concrete: `hooks.LoadEnvOverlay`'s `from_file` resolver refused every symlink anywhere in the path, via `dirfd.ReadUnderRootNoFollow`. A Kubernetes projected-secret volume's on-disk layout is *entirely* symlinks two levels deep (`key -> ..data/key`, `..data -> ..<timestamp>`), so this was a hard, unconditional break for that entire class of secret mount — not a corner case.

The interesting design constraint was in the brief itself: resolve a permitted symlink "through the fd-anchored walk and never through a path re-lookup." That rules out the obvious approach (`os.Readlink` + `filepath.Join` + re-`open` by string), which is exactly what `filepath.EvalSymlinks` and this codebase's own `VerifyRootOwnedExecutable` do — and *why* that's acceptable for `VerifyRootOwnedExecutable` but not here took some working out: `VerifyRootOwnedExecutable` restarts its walk from `/` on every hop, but every hop it's willing to trust must independently prove itself root-or-self-owned before the walk continues, so a race that swaps something mid-walk can only ever land it on something *also* independently verified, never anything the walk hasn't itself checked. For `from_file`'s allowed-root containment, the equivalent property doesn't hold — the root is a boundary the *caller* controls, not necessarily one the path's owner controls, so restarting from a string between hops really would reopen a TOCTOU a workload could exploit to redirect the walk outside the root.

So the fix keeps one directory fd anchored across the whole walk (never re-opened from a string), and on a no-follow-open failure, reads the symlink's target via `unix.Readlinkat` against that same fd, splicing the target's components into the remaining path and continuing the loop.

**A wrong assumption cost real debugging time:** I assumed an `O_DIRECTORY|O_NOFOLLOW` open of a symlink would fail `ELOOP`, the same as a plain `O_NOFOLLOW` open does for a leaf. It doesn't — it fails `ENOTDIR`, indistinguishable by errno alone from "this component is a plain regular file, not a directory" (a genuinely different, non-symlink error the walk must still propagate as a hard failure). Caught by the first test run (`TestReadUnderRootNoFollow_AllowsProjectedSecretStyleSymlinkChain` failing with "not a directory" instead of resolving), confirmed with a two-line standalone repro (`syscall.Open(link, O_DIRECTORY|O_NOFOLLOW, ...)` on a real symlink) before trusting the fix. The actual fix: `isSymlinkAt` does an explicit `Fstatat(..., AT_SYMLINK_NOFOLLOW)` on the same name to positively confirm "this is a symlink" before treating the failure as one to resolve, rather than inferring symlink-ness from which errno came back.

**Scope decisions, deliberately conservative:** an absolute symlink target is refused outright (`ErrPathEscapesRoot`), even one that would numerically resolve back inside root — proving that without trusting the target's own text isn't possible with this walk's guarantees, and no legitimate k8s/ConfigMap layout ever uses one. A target containing `..` is refused the same way, for the same reason (supporting it safely would need an explicit fd stack to make `..` pop to an already-verified ancestor rather than trusting the kernel's own `..` resolution from an arbitrary point in the tree, which is more machinery than any real caller needs — k8s's own symlinks are always plain, single-component, sibling-relative names). A hop cap of 20 (matching `VerifyRootOwnedExecutable`'s own headroom) guards a symlink loop.

One existing test had to be *inverted*, not just updated: `TestReadUnderRootNoFollow_RefusesIntermediateSymlinkInsideRoot` previously proved the old, stricter behavior (refuse even an intermediate symlink whose target is also under root). That's exactly the case the fix is meant to allow, so it's renamed to `_AllowsIntermediateSymlinkInsideRoot` and now asserts success — a reviewer diffing just the test file should read this as "the policy changed, on purpose," not as a weakened test.

## R9(b): two iterations, because the first one solved the wrong problem

My first pass followed the brief's own suggested framing literally: "follow it when the target is owned by the workload user, or warn loudly." I built `dirfd.ReadFileNoFollowOwnedBy`, a full symlink-chain walker checking per-hop ownership against a caller-supplied uid (structurally similar to `VerifyRootOwnedExecutable`, but for "owned by uid N" instead of "owned by root or self"), and wired it into `configureSharedWorkspaceGit` as a fallback when the plain no-follow read failed.

A design-authority addendum arrived mid-task and overruled this, with a rationale I hadn't fully weighed: **following the link at all means root opens a workload-controlled path with follow, before any ownership check can run.** My chain-walker's own ownership check happens via `Fstatat`/`Readlinkat` against an already-*opened* fd — but that "already opened" step is itself the exposure: a workload can plant a FIFO or a device node at the symlink's target, and the open (even one that will be immediately fstat-checked and rejected once its type is known) can hang or have side effects before rejection. My design's own `readRegularOwnedAt` does check type via fstat before reading content, but it still has to *open* first — for a FIFO, that's a blocking (or, since I used `O_NONBLOCK`, at least a "some fd got opened") interaction with something the workload fully controls. The original unconditional refusal never opens anything questionable in the first place; it fails at the `O_NOFOLLOW` open itself. That's a small but real difference in attack surface, and the ruling weighs it against a comparatively small usability win (dotfile managers aren't the common case sciontool runs against). I think the ruling is right, in retrospect the "follow if owned" framing in the original brief text undersold this specific risk.

Practically, this meant deleting code I'd just written and tested (`ReadFileNoFollowOwnedBy`, `readRegularOwnedAt`, `ErrSymlinkChainNotOwnedByUID`, and eight tests) rather than adapting it — there was no way to keep the "open then check" shape and satisfy "never open a workload-controlled path with follow." I kept the deleted commit in branch history rather than rewriting it away (per the addendum's own "add follow-up commits, don't branch anew" instruction), so the false start is visible to a reviewer rather than silently erased.

The actual fix is much smaller than the false start: keep the original refusal exactly as it was, add one `log.Warn` (a new level; `pkg/sciontool/log` only had `Info`/`Error`/`Debug`) naming the path and the dirfd sentinel's own reason text, explicitly never the file's content. Since every one of the four refusal reasons (symlink, FIFO, hardlink, oversize) already flows through the identical `dirfd.ReadFileNoFollow` error branch in `configureSharedWorkspaceGit`, one warn call covers all four without any extra branching — worth noting because it would have been easy to over-engineer four separate messages for what the ruling describes as needing "the same WARN."

## R8 writer-merge: arriving at a fork another agent had already found and correctly refused to force

The addendum folded this in because it's coupled to R9(b) — both touch the gitconfig install path. Before writing any code I read `scion/substrate-refactor-moves`'s section of the shared report (that branch also cut from the same R1/R5 tip, for R10), and found it had already hit this exact question and **stopped**, explicitly declining to force a merge between `dirfd.WriteFileNoFollow` (always replaces the leaf) and `hub.WriteFileNoFollowChown` (refuses a non-regular leaf outright) without a design ruling — correctly identifying that either direction is an observable behavior change for a real caller, and that it was likely coupled to R9(b)'s open question. That framing is exactly right, and the addendum's ruling (option c: one core, two named policies) is the ruling that unblocks it. Worth recording for whoever integrates both branches: `dirfd.WriteFileNoFollow` and `hub.WriteFileNoFollowChown` are **unchanged** on `scion/substrate-refactor-moves` and **merged** on this branch — that's not a conflict to be alarmed by, it's the fan-out coordinator (sb-em) reassigning ownership of a blocked item mid-flight, but it does mean an integration step needs to reconcile which branch's version of those two functions wins (this branch's, per the ruling).

Implementation notes:

- The `LeafPolicy` enum's "no usable zero value" requirement is enforced by treating `LeafPolicyUnset` (the zero value) as an explicit runtime error from `WriteFileNoFollow`/`WriteFileNoFollowWithChown`, rather than, say, a lint-only convention. A test (`TestWriteFileNoFollow_InvalidLeafPolicyRejected`) proves the zero value is actually rejected, not just documented as invalid.
- The one non-obvious wrinkle in "hub's `WriteFileNoFollowChown` becomes a thin wrapper": hub's existing tests intercept `fchownFn`, a package-level var, specifically so they can assert a chown ran with the right uid/gid *without* needing `CAP_CHOWN` to actually perform an arbitrary chown as a non-root test process. If the merged core called `syscall.Fchown` directly, that seam would go dead (tests asserting `chownCalled` would either falsely pass — never invoked, so trivially "not called" for the refusal-path tests — or, worse, the *success*-path test would try a real chown to uid 1000 and fail outright, since the test process isn't root). Fixed by threading the chown function through as an explicit parameter (`WriteFileNoFollowWithChown`) rather than promoting `fchownFn`-style dependency injection into `dirfd` as a second global var; `hub.WriteFileNoFollowChown` passes its own existing `fchownFn` through on every call, so the seam keeps working with zero test changes. Confirmed by running the full `hub` suite, not just the one named-in-the-addendum test — several other tests in that package also depend on this seam for the success path, and would have been silent casualties of a naive "just call syscall.Fchown from dirfd" merge.
- fsync's ordering relative to fchmod/fchown flipped from hub's prior behavior (hub synced *before* those calls; the ruling's stated order — fsync last, right before rename — is what's implemented now). Called out explicitly in the commit body since it's a real, if minor, behavior change nobody asked for by name but that the ruling's wording implies.

## R9(c): the "evidence" was concrete, but the packaged integration test wasn't cooperating, and chasing why was itself informative

The historical `EvalSymlinks` removal was already done (a prior commit, `6a5afedea`, replaced `os.Executable()` + `filepath.EvalSymlinks` with `rootexec.SelfExe()` = the literal string `/proc/self/exe`). R9(c) asks to confirm this is safe, not to change it, so the question was purely evidentiary.

The repo already has `TestReExecIntegration`, gated behind `SCION_INTEGRATION_TEST=1`, that builds a real `sciontool` binary and drives the exact re-exec path with a staged secret, checking both the child's environment and the parent's own `/proc/<pid>/environ` afterward. Running it in this sandbox (which is a real Docker container — `/.dockerenv` present, kernel 6.8.0) failed both assertions. Before concluding anything about the re-exec itself, I checked two things in order:

1. **Is this actually exercising the re-exec, or is something upstream of it broken?** A hand-built reproduction of the exact same binary, invoked directly (not through the test harness) with matching env, succeeded cleanly — `ENV_CLEAN`/`PROC_CLEAN`, the log showing the re-exec's own "Re-execing..." line followed by the same pid restarting `init`'s startup sequence. This is strong direct evidence the exec/kernel-level behavior is fine.
2. **Is the packaged test's failure something this branch caused?** Checked against the unmodified base commit in a detached worktree (`git worktree add --detach /tmp/r9c-base 71ad0ec6...`) — byte-identical two-assertion failure, before this branch had touched `reExecWithCleanEnv` at all. Pre-existing, not a regression.

I partially chased the root cause of the packaged test's own failure (not required, but cheap once already instrumenting): `resolveAgentHome` (`init.go`) ignores `$HOME` entirely whenever `targetUID == 0 && rootless == true` — which is this sandbox's actual state (already running as the "scion" uid) — and looks up `/etc/passwd` instead. That means the test's per-test `HOME` isolation (`t.TempDir()`) never actually takes effect in this environment; the process runs against the real, shared `/home/scion`. I did *not* find the actual mechanism connecting that to the specific two failed assertions (several controlled reproductions using the identical duplicate/shared-`HOME` shape all still passed), so I'm recording it as a documented lead, not a root cause, and declining to chase it further — it's orthogonal to R9(c) and the manual reproduction already answers the actual question asked.

The corresponding commit is comment-only — no code changed — with the evidence written directly into `reExecWithCleanEnv`'s doc comment, on the theory that a future reader who sees a lone `syscall.Exec` call with no visible symlink-safety handling is exactly the person who might "fix" it by adding `EvalSymlinks` back, and the reasoning needs to be where they'll see it, not just in a commit message or a project log.

## Side effect: a pure doc-comment addition broke an unrelated, brittle-by-design guard test

`pkg/sciontool/rootexec/guard_test.go` tracks an allowlist of exec call sites in `init.go` keyed by *exact line number*. Adding 36 lines of doc comment to `reExecWithCleanEnv` (which sits well above every tracked call site) shifted all 16 entries by the same 36 lines — except one, which sits *after* `configureSharedWorkspaceGit`'s gitconfig-refusal block, whose net line count also changed across my two R9(b) commits, so that one entry needed a different offset than the uniform +36 I applied everywhere else. Caught immediately by re-running the full `./pkg/sciontool/...` sweep (not just the packages I'd been editing) before considering the work done — a habit worth calling out here since it's exactly the kind of gate a narrower "only test what I touched" pass would have missed, since `rootexec` isn't a package this item's diff otherwise touches at all. `scion/substrate-refactor-init` (the R3+R4 fan-out) hit the identical category of breakage for the identical reason (their line-count changes from moving code, not adding comments) — this seems likely to recur for any fan-out branch that changes `init.go`'s line count, worth flagging to sb-em as a maintenance cost of that guard's design, not something to "fix" unilaterally here.

## Round-3 review fixes (`b069da57a`)

A fresh reviewer's round-3 pass came back REQUEST CHANGES/LOW risk: the security core was confirmed sound (R9(a) escape-safe, R9(b) refuse+WARN never-follow, R8's `LeafPolicy` sound), but flagged three real issues plus a few optional cleanups:

- **Comment hygiene.** Every "R9(a)"/"R9(b)"/"R9(c)"/"RULED (design authority)" reference in permanent source and test comments was flagged for removal — this branch's earlier commits carried plan-item IDs and internal process framing into comments that ship upstream, which the standing rule against "bare #N, finding IDs, process vocabulary" already covers; I'd missed applying it retroactively to comments written before the addendum arrived. Reworded all seven flagged locations to keep the technical rationale (why the behavior is what it is) while dropping the internal framing (which plan item asked for it, who ruled on it). Also used this pass to trim `reExecWithCleanEnv`'s doc comment from 35 lines to 12 — the original had grown into something closer to a mini incident report than a doc comment, which is exactly the shape a project-log entry should hold instead. **This is the second time in this branch's history that editing `reExecWithCleanEnv`'s comment shifted every line number below it in `init.go` and broke `pkg/sciontool/rootexec/guard_test.go`'s line-keyed allowlist** (first time: adding the comment; this time: shrinking it). Recomputed the allowlist in the same commit both times. This guard's design cost is now demonstrated twice on this branch alone (plus once on `scion/substrate-refactor-init` for an unrelated code-move reason) — flagging again that this seems like a real, recurring maintenance tax rather than a one-off, though changing the guard's own design is out of scope for this item.
- **A real correctness gap in the WARN wording**, not just a wording nitpick: the message said "is not a regular file ... Replace it with a regular file" unconditionally, but that specific refusal branch also fires for an oversized *regular* file and for a parent-directory-walk I/O error, where "not a regular file" is simply false. Fixed by making the wording reason-agnostic and letting `%v` (the actual dirfd sentinel error) carry the specific reason, with the byte-bound in the remedy text sourced from the real `gitconfigMaxBytes` constant instead of a hardcoded "regular file" phrase.
- **A genuine test coverage gap**, also not cosmetic: every existing "does the walk correctly refuse an escaping symlink target" test planted the symlink at the *leaf* of the read path. `ReadUnderRootNoFollow` resolves a leaf symlink through a different failure mode (`ReadAtNoFollow`'s own `O_NOFOLLOW` open, which fails `ELOOP`) than an *intermediate* one (an `O_DIRECTORY|O_NOFOLLOW` open, which fails `ENOTDIR` — the exact asymmetry `isSymlinkAt` exists to paper over, see the R9(a) section above). So the existing tests, despite exercising "escape via absolute target" and "escape via `..`" in the abstract, never actually exercised the code path an intermediate escaping symlink takes. Added a 4-case table test: absolute-target intermediate symlink, `..`-target intermediate symlink, the same one level deeper under a real subdirectory (to prove the `..`-count isn't hardcoded to depth 1), and a chained case where a splice that looks safe on its own face (`chain -> "d/up"`, no `..`, no leading `/`) resolves one hop later into an escaping symlink — proving the loop actually re-validates every hop it splices in, not just the first one.

Also addressed (optional per the reviewer, done anyway since they were cheap and real): a stale `safeio.go` comment that said both branches "fall through here via ELOOP" when one of them actually falls through via `isSymlinkAt`'s explicit type check, not that specific errno; `hub.WriteFileNoFollowChown`'s error wrap said "refusing to write" unconditionally, which is misleading for a plain I/O failure partway through the write (a full disk, say) that isn't a refusal at all.

`TestClient_StartTokenRefresh_RefusesSymlinkAtTokenPath` confirmed untouched (`git diff --stat` on the file shows nothing). Full gate sweep (`./pkg/sciontool/...`, `./cmd/...`, `./pkg/config/...`, `./pkg/runtime/...`, `./pkg/runtimebroker/...`) green at the new head, `b069da57a`.
