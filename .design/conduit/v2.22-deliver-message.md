### Freeze gaps
Places where re-anchoring shows the draft no longer fits the code. Each has a proposed resolution. **G1 changes the reviewed bind rule (the sec Required item) and needs a decision before the hub bind is built.** The rest are implementation choices inside the draft's intent.

- **G1. Rows can still be `pending` when the broker delivers (blocking for §2.1 check 5 and §2.6).** The draft's bind requires every row to be `dispatched`. On main the agent-DM path (`ExecuteAgentDM`) persists the row `pending` (pkg/hub/agent_dm_operation.go:462) and flips it to `dispatched` only after the broker call returns (`markDispatched`, :740). An interrupt is delivered synchronously inside that broker call, so its `/deliver` would always meet a `pending` row and get 409 `bound`. A buffered flush (2 s later) usually meets `dispatched`, but can race a slow `markDispatched`. Other writers (chat, notifications, broadcast) insert rows already `dispatched`, so they fit.
  *Proposed:* the bind accepts rows in `pending` **or** `dispatched` (both mean "authorized at the message route and not yet delivered"; `failed`, `deferred`, `no_recipient` and the new states are still refused). The unbind returns rows to `dispatched`. `MarkMessageDispatched` keeps its `pending`-only compare-and-set, so a row the bind already moved is a CAS miss there, which the caller already treats as benign (agent_dm_operation.go:761-766). The broker's identity, recipient and same-id rules are unchanged.
- **G2. "The agent advertises `deliver-message`, as reported by the hub" has no mechanism (§1.5, broker check 2).** The broker has no view of an agent's Hello. *Proposed:* the hub is the one that checks advertisement, at call time (`ErrAgentControlNotAdvertised`, mapped to "not reached", which leads to exec fallback). The broker only calls `/deliver` for an agent it launched with the flag: the hub adds `hub.conduit_deliver` to the agent experiments (`SCION_HUB_EXPERIMENTS`) and the dispatch experiments only while `hub.conduit` is also served. The broker records the launch flag with the agent. An agent launched without it never causes a `/deliver` call (A2, A3). In Phase A the switch applies to Cloud Run only. Docker and Kubernetes stay on exec (§7 Phase B, opt-in per broker, is later work); tests can enable other runtimes.
- **G3. Key allowlist is narrower on main (§5.3).** The draft lists eight key names. `tmuxdeliver` deliberately allows only `Enter`, `Escape`, `C-c`, the keys the shipped harnesses use (pkg/agent/tmuxdeliver/bounds.go:25-41), and leaves out `C-d` and the others so that a delivery can never end a harness. This only narrows the draft. The frozen allowlist is the code's three keys; widening still needs security review (§1.7).
- **G4. `ready.nonce` in the request is redundant (§1.2).** `tmuxdeliver.Wait` reads the init-run nonce and the ready spec (line 2) from the container's own files and caps them with `MaxDeadline`/`MaxSettle` (ready.go `WaitConfig`). A caller-supplied nonce could only let the caller claim readiness. *Proposed:* the request `ready` block is `{strategy, settle_ms, timeout_ms}`, used as the fallback timings when the image writes no line 2. An unknown `nonce` field is refused like any unknown field.
- **G5. A `partial` row would lose today's failure notice (§1.4, §2.6).** On the exec path a partial delivery reaches the broker's failure handler, and `/message-failures` marks the row `failed` and sends the DELIVERY_FAILED notice. It acts only on `pending`/`dispatched` rows (pkg/hub/message_delivery_failures.go:219-222). A conduit row the hub already set to `partial` would therefore get no notice and no Failed badge. *Proposed:* `/message-failures` also accepts `partial` rows: it moves them to `failed` with the reason and sends the notice. `delivery_id` and `delivery_outcome` are kept, so a same-id replay still returns the stored outcome without calling the agent. `delivered` rows are never failed.
- **G6. `requires: hub.conduit` is not a registry field (§6.1).** The registry has no `Requires`. *Proposed:* the hub checks both flags itself: `/deliver` answers 404 unless `hub.conduit_deliver` is on **and** conduit is served (`conduitRoutable`); the launch flag is sent only under the same condition.
- **G7. The broker-side readiness wait moves to sciontool for conduit flushes (§3.1).** Today the buffer waits for readiness *before* taking the messages, so messages that arrive during the wait join the flush (msgbuffer.go:303-330). A conduit flush cannot probe from the broker (no exec on Cloud Run), so the broker skips its own wait and sciontool waits instead (`op=paste`). Messages that arrive during sciontool's wait go into the next flush. Ordering and at-most-once are unchanged.

## 0. Decision summary

- sciontool gets one new control route, `deliver-message`. It runs a single *flush* locally: optional interrupt keys, the readiness wait, a bracketed paste through a named buffer, then the submit keys. All tmux argv is built inside sciontool from a fixed schema. There is no shell and no caller-supplied argv.
- The **broker stays the delivery orchestrator**: the debounce buffer, the per-container lock, the harness DeliverySpec resolution, the pre-paste retry rule, `PartialDeliveryError`, and async failure reporting. Only the *transport* of one flush changes, from runtime exec to a conduit RPC. This keeps delivery logic in one place, which is the first variant in the excerpt's C1 section.
- The broker has no agent-RPC caller of its own, so the path is **broker → hub → agent**. A new broker-authenticated hub endpoint validates the call and forwards it with `callAgentControl`.
- **The hub binds each delivery to its message rows atomically** (§2.6): `dispatched → delivering` in one transaction, with the `delivery_id` recorded. A second delivery of the same row under any other id never reaches the agent.
- The route has four ops matching every `deliverImmediate` shape: paste, interrupt then paste, submit only, interrupt then submit (R1). Narrow route bounds apply, with exec fallback or a named failure and never clamping; all shipped harnesses fit (§1.7, R2). A hard deadline in sciontool and a split 409 mean a timed-out call can never paste late (§2.2, R3).
- The readiness and paste steps live in one shared leaf package, `pkg/agent/tmuxdeliver` (§3.4), used by both the broker's exec path and sciontool. It also strips paste-mode markers and C0 controls (§5.3), so both paths behave identically.
- v1 carries **text and interrupts only**. Attachments and raw keys stay off the route (see §1.6 and §3.3).
- The route sits behind a registered experiment, `hub.conduit_deliver` (server layer), on top of `hub.conduit`. It is advertised in `Hello.capabilities.rpc` only when enabled. Rollout starts with Cloud Run, where it removes the IAP exec dependency. Existing agents pick it up only after a restart (§7).

## 1. Wire

### 1.1 Control route
- Route: `POST /v1/control/deliver-message` on the existing control handler. `Prefix` is `/v1/control/` (pkg/sciontool/control/handler.go:33). The existing route is `rotate-token` (:40).
- It arrives as a unary `RpcRequest` frame over the agent's own outbound session. sciontool's RPC adapter (control/rpc.go:34) accepts only clean paths (`allowedPath`, :81-85) and forwards only `Content-Type` (:59-63). So every input is in the JSON body; headers carry nothing.
- Handler rule change (§3.7): today's routes must be idempotent or coalescing. `deliver-message` is neither naturally, so it is made **idempotent by key** (§2.4): a replay returns the stored outcome and never acts twice. The other §3.7 rules stay: POST only, 404 for an unknown route, 405 for any other method, and no credentials in either direction.

### 1.2 Request (JSON, `Content-Type: application/json`)
| field | type | rule |
|---|---|---|
| `v` | int | `1`; any other value → 400 |
| `delivery_id` | string | `^[A-Za-z0-9-]{1,64}$`. This is the broker flush nonce, which already names the tmux buffer `scion-msg-<nonce>-<n>`. It is the idempotency key. The hub records it against the message rows on the first bind and refuses any other id for those rows (§2.6). |
| `broker_id` | string | **Set by the hub**, which overwrites any value the broker sent (§5.7). Part of the key scope. |
| `message_ids` | []string | **1..64** ids, each `^[A-Za-z0-9-]{1,64}$`. Required for every op, including `interrupt_paste` and `interrupt_submit` (§2.1, A3, R4). The hub binds the delivery to these rows (§2.6). |
| `op` | enum | `paste`, `interrupt_paste`, `submit_only` or `interrupt_submit` (R1). Each maps one `deliverImmediate` shape (§3.1): `paste` is text then submit; `interrupt_paste` is interrupt keys then text then submit, in one locked call; `submit_only` (empty message, for confirmations) sends the submit keys once, with no extra submits; `interrupt_submit` (interrupt with empty text) sends the interrupt keys then the submit keys once. |
| `text` | string | required and non-empty for `paste` and `interrupt_paste`; must be absent for the other two. UTF-8, at most `MaxDeliverText` = 512 KiB. |
| `interrupt_keys` | []key | 1..4 for the `interrupt_*` ops, absent otherwise; from the key allowlist (§5.3). This is the harness's `interrupt_sequence`, or its single `interrupt_key`. |
| `deadline_ms` | int | ≤ 92000. A hard stop measured from receipt (R3). |
| `not_after_unix_ms` | int | **Set by the hub**: its send time + 92 s (Q3b). The broker's value is overwritten. sciontool's hard stop is the **earlier** of receipt + `deadline_ms` and `not_after_unix_ms`, subject to a **skew guard**. If `not_after_unix_ms` is already past at receipt, or earlier than receipt + `deadline_ms` − 30 s, sciontool treats it as clock skew: it ignores it, uses receipt + `deadline_ms`, and logs a skew warning (counts only). sciontool **never starts the paste** (or, for the `*_submit` ops, the first key) after the hard stop, and answers 408 `expired_before_paste` (§2.2). |
| `submit_keys` | []key | at most 4, from the allowlist |
| `extra_submits` | {`count` ≤ 3, `delay_ms` ≤ 2000} | from the harness DeliverySpec |
| `ready` | {`strategy`: `hook`\|`delay`, `settle_ms` ≤ 10000, `timeout_ms` ≤ 90000, `nonce`} or absent | the readiness wait for `paste` only, from the harness ready block (§3.1). The `interrupt_*` ops and `submit_only` skip readiness, as `deliverImmediate` does today. |

The broker resolves the per-harness DeliverySpec (excerpt: "a delivery request would carry the resolved settings with it"). sciontool still validates every field against fixed bounds, so a wrong or hostile DeliverySpec cannot widen what the route can do.

### 1.3 Responses
| code | meaning | broker treatment |
|---|---|---|
| 200 `{"outcome":"delivered","replayed":bool}` | pasted and submitted | ack (delivered) |
| 200 `{"outcome":"partial","stage":"interrupt"\|"load_buffer"\|"paste"\|"submit"\|"extra_submit","replayed":bool}` | a visible step had started (interrupt keys or paste-buffer) and a step failed; `stage` names the first failed step | `PartialDeliveryError`, no retry |
| 409 `{"outcome":"in_progress"}` | the **same** key is already running | no retry; treated as partial (unknown) |
| 409 `{"outcome":"busy"}` | a **different** key is running (R3); nothing was done for this key | not reached: the hub unbinds, and the broker retries under the pre-paste rule |
| 408 `{"outcome":"expired_before_paste"}` | the hard stop (§1.2) passed before the paste or first key; nothing was pasted | not reached; no retry (it has already taken up to ~92 s); the hub unbinds and the broker reports a failure with reason `expired before paste` |
| hub 409 `{"outcome":"bound"}` | a row is already `delivering` under another id, or is past `delivering` (§2.6). Never forwarded to the agent. | no retry, no exec fallback; report to the hub as a broker error |
| hub 200 with a stored outcome, `replayed:true` | the rows already reached a final state under this same id | treat as that outcome |
| 400 | schema or bounds violation | permanent failure before paste; report |
| 404 | route not served (experiment off) | fall back to exec if the runtime supports it, else report |
| 422 `{"stage":"target"\|"load_buffer"}` | tmux target missing (harness not up), or staging the text failed before any visible step | failure before paste; not stored by the key store; retryable (§2.5) |
| 413 | body over `MaxRPCBody` (session-level, conduit/session.go) | failure before paste; fall back to exec or report |
| 429 / 503 / 501 (session-level) | concurrency / draining / no handler | failure before paste; retryable |

Callers (S4, the broker) key on the status code and `outcome`, never on a particular `stage` value; `stage` is diagnostic. (r3.1 amendment: the 422 `load_buffer` stage and the partial stages, from the S2 review; a failure before any visible step is not stored, so a retry with the same `delivery_id` runs.)

The hub endpoint passes these through as `AgentControlStatusError` (pkg/hub/conduit_agent_control.go:56-64). `ErrNoSession` and `ErrAgentControlNotAdvertised` map to "not reached".

### 1.4 Async failure
The RPC is synchronous, so the outcome is known at the broker. Async failure reporting is unchanged: the broker's failure handler, `reportMessageFailure` (pkg/runtimebroker/message_failures.go:35), sends it to the hub's `MarkMessageFailed`. No new hub-side async path.

### 1.5 `Hello.capabilities.rpc`
`Capabilities.rpc` (proto/conduit/v1/conduit.proto:83-85) is filled from `ctl.Routes()` (handler.go:78), passed as `RPCRoutes` (cmd/sciontool/commands/init_conduit.go:115-116; pkg/sciontool/conduit/agent.go:173-176, sent in Hello at :361). sciontool registers `deliver-message` only when **all** of these hold:
1. the agent env has the experiment flag the broker sets at create time;
2. `tmux` is on PATH, the same pre-flight as cmd/sciontool/commands/init.go:1172;
3. sciontool is running the harness in the `scion` tmux session.

The hub checks `GetRpc()` before calling (pkg/hub/conduit_agent_control.go:117). If the route is not advertised, the broker falls back to exec, or reports the message as failed where there is no exec.

The broker's "use conduit transport?" check (§3.2.5) requires **all four**:
- the experiment is on at the hub;
- the agent currently advertises `deliver-message` in its `Hello.capabilities.rpc`, as reported by the hub;
- the hub endpoint answers;
- the resolved delivery, ready and interrupt settings fit the route bounds (§1.7), and the flush has at least one message id.

The experiment flag reaches sciontool only through the agent env at create time, so **an agent created before the experiment was turned on does not register the route until it is restarted**. Until then it doesn't advertise the route, and the broker keeps using exec for it (§7).

### 1.6 Size and streaming
- `MaxRPCBody` is 768 KiB (pkg/conduit/config.go:41). `MaxDeliverText` is 512 KiB, which leaves room for JSON escaping. Larger text gets 413 and goes through exec where available; otherwise it is reported as failed before paste.
- There is no streaming for text. Stream kinds stay tcp/pty/ssh/logs/events (pkg/conduit/kinds.go:63-67).
- Attachments (10 MB each, 10 per message, pkg/hub/attachments.go:77-79) do not fit unary RPC. They are **out of v1**. A message with attachments to a conduit-delivery agent takes the exec path where the runtime has one. Where it has none, the existing outcome applies: undelivered files become "not delivered" lines in the text, with per-file outcomes reported. A later phase can add a chunked `deliver-attachment` route under the §5.4 rules.

### 1.7 Route bounds and harness config (R2)
The route keeps a **narrow** set of bounds for v1, which sec-review-3 and conduit-lead agreed. Harness config allows more (pkg/config/settings_v1.go:3343-3352 and `validateSubmitKey` :3497; pkg/agent/state/state.go:68-77):

| setting | harness config allows | route allows (v1) |
|---|---|---|
| submit keys | 1..4, any 1-32 byte name | 1..4, from the 8-name allowlist (§5.3) |
| interrupt key or sequence | free-form, no count cap | 1..4, from the allowlist |
| extra submits | ≤ 5 | ≤ 3 |
| extra submit delay | ≤ 5 s | ≤ 2 s |
| ready settle | ≤ 60 s | ≤ 10 s |
| ready timeout | 10 s to 10 min | ≤ 90 s |

**No silent clamping.** The broker checks the resolved DeliverySpec, ReadySpec and interrupt keys against the route bounds *before* choosing conduit transport. If anything falls outside them, the broker uses exec where the runtime has it. Otherwise it reports a failure before paste with the reason `delivery settings outside conduit route bounds: <field>` (the field name only, no values). sciontool repeats the checks and answers 400 if anything is out of bounds; it never adjusts a value.

**The shipped harnesses all fit** (harnesses/*/config.yaml: antigravity, claude, codex, copilot, gemini-cli, grok-build, hermes, muse-code, opencode, pi):
- submit keys `[Enter]`; extra submits 2; delay 300 ms;
- interrupt `C-c` or `Escape`; claude uses the sequence `[Escape, C-c]`;
- ready `hook` with settle 1.5 s and timeout 90 s (claude, gemini-cli, grok-build), or `delay` with settle 8 s (the rest).

The keys used are `Enter`, `Escape` and `C-c`, all on the allowlist. Cloud Run with shipped harnesses therefore uses the route. A test pins this: it loads every shipped harness config and asserts that it fits the route bounds, so a new harness or a config change that leaves the bounds fails CI instead of silently falling back.

Widening the allowlist or the bounds needs sec-review-3's review, with the list of shipped harness keys. Reusing `validateSubmitKey` on the route is not allowed, because it accepts any key name.

## 2. Hub side

### 2.1 Caller
The hub never starts a delivery. It **relays** one: new endpoint `POST /api/v1/runtime-brokers/{brokerId}/agents/{agentId}/deliver`, authenticated as the broker principal (the same broker auth as `/message-failures`, pkg/hub/message_delivery_failures.go). Checks, in order:
1. the experiment is on (`requireExperiment`, pkg/hub/experiments.go:126);
2. the path broker is the caller and is the agent's current broker;
3. the agent id is resolved from the path through the store, never from the body;
4. every `message_ids` row exists and names this agent as recipient. These rows were written only after `authorizeAgentMessage` passed (§5.1). Check 4 does **not** test state (Q2). The §2.6 bind rules decide state, so a same-id retry and a final-state replay reach those rules.
5. the **atomic bind** (§2.6): in one transaction, every named row moves `dispatched → delivering` with this `delivery_id` recorded. If any row is in another state, the transaction is refused and nothing changes. A retry under the same id on rows already `delivering` with that id passes.

**Interrupts (A3).** An interrupt is not a separate kind of request. It is the `interrupt` flag on `POST /api/v1/agents/{id}/message` (pkg/hub/handlers_agent_messaging.go:1990), so every interrupt has a message row that went through `authorizeAgentMessage` and reached `dispatched` like any message. The broker delivers interrupts unbuffered, one message per flush. So an `interrupt_paste` or `interrupt_submit` flush carries exactly one message id and goes through the same checks 1-5. A flush without a message id (no hub row) never uses conduit transport; it uses exec, or fails where there is no exec. The route rejects empty `message_ids` with 400, and the hub rejects it before binding.

**Authz catalog entry (A1).** The endpoint gets an entry in pkg/hub/authzop/catalog_brokers.go, modelled on `broker.messagefailures.report` (pkg/hub/authzop/catalog_brokers.go:225-246):
- ID `broker.agent.deliver`, domain `broker`;
- EntryPoint `POST /api/v1/runtime-brokers/{id}/agents/{agentId}/deliver`;
- Principals `PrincipalBroker`, Credentials `CredentialBrokerToken`, ResourceResolver `broker-self` plus the agent-assignment check;
- Effects `EffectUpdateResource` (the row state) plus the agent call;
- DenialCodes `DenialForbidden`, plus the new 409 `bound`;
- an `ExemptionInternalOnly` waiving the base permission: the broker uses its own HMAC credential for an agent assigned to it, and user authority was already checked at the message route (§5.1);
- `Bearer: NonUser()`;
- TestRefs include `TestBearerDisposition_EveryRoutePatternCovered` plus the endpoint's own tests (§6.3).

The R274(d) identifier and string checks for the implementing PR must include `broker.agent.deliver`, the route pattern, and the new dispatch states (§2.6).

### 2.2 Routing
Unchanged: `router.Request{OpStatefulRPC, PrincipalAgent}`, local session or relay `RemoteSession` (pkg/conduit/router/router.go, resolution ending at :287), and re-resolution on a stale owner (bounded by `MaxReResolves`, :34). **Timeouts (A4, with R3).** The budget is laid out so a late paste is impossible, not just unlikely:

| bound | value | why |
|---|---|---|
| readiness wait (paste only) | ≤ 90 s from receipt | the shipped hook harnesses use `timeout: 90s` (§1.7), so the route keeps the exec path's semantics exactly |
| sciontool hard stop `deadline_ms` | 92 s from receipt | no paste or first key starts after it (R3) |
| paste and submits after start | ≤ 8 s | load-buffer, paste and submit, plus at most 3 extra submits × 2 s |
| hub `callAgentControl` timeout, this route | **110 s** | above 92 + 8 = 100 s, a 10 s margin |
| relay `DefaultRPCTimeout` | 120 s | 10 s above the hub's |
| broker wait on `/deliver` | 115 s | it outlasts the hub and sees the hub's answer |

The draft first lowered readiness to 80 s. That would have pushed every shipped hook harness off the route (§1.7), so instead sciontool gets a hard deadline. Because sciontool cannot start a paste after 92 s, a hub timeout at 110 s can only cut off the tail of a paste that has already started. That case is already classed as partial with no retry. The 10 s margins cover a relay hop and a re-resolve; they no longer protect against a late paste.

**Send-to-receipt delay (Q3).** The 92 s hard stop on the receipt side is counted from sciontool's *receipt*, but the hub's 110 s from its *send*. The delay between them comes from the relay hop, re-resolve, the session window and `MaxConcurrentRPCs` queueing. It eats into the 18 s. Two guards:
- **Mechanical bound (Q3b):** the hub sends `not_after_unix_ms` = send time + 92 s, and sciontool uses the earlier of that and receipt + 92 s (§1.2). With synchronised clocks, no paste starts later than 92 s after the hub's send, whatever the delay.
  - **Skew guard:** if `not_after` is already past at receipt, or earlier than receipt + 92 s − 30 s, sciontool ignores it and uses receipt + 92 s, logging a skew warning (counts only, no times or ids). An agent clock far ahead of the hub's (for example by 120 s) therefore still pastes, with the receipt bound, instead of every delivery expiring with no exec fallback.
  - Within the 30 s tolerance, an agent clock ahead of the hub's shortens the window by up to 30 s. An agent clock behind falls back to the receipt bound. In both cases nothing is pasted late beyond the receipt bound.
  - The bound is therefore only as good as clock sync. Hub and agent hosts are expected to be NTP-synchronised; Cloud Run's clock is. sciontool logs the observed skew at debug, and criterion 19 records it.
- **Stated assumption, the backstop:** the send-to-receipt delay is at most 10 s. If both guards fail (heavy skew plus a delay over about 18 s), the residual outcome is bounded: the hub has already timed out, so the rows are `partial` (§2.6) and the paste is a *late* paste, **never a duplicate**. The next flush meets sciontool still busy, gets 409 `busy` (not reached), and retries under the pre-paste rule.

**Paste time is an expectation, not yet measured.** A 512 KiB body is expected to finish within the 18 s between the hard stop (92 s) and the hub timeout (110 s). The steps are load-buffer from stdin, a bracketed paste, one submit pass, and at most 3 extra submits × 2 s. The stdin load and the paste are local tmux operations inside the container, with no exec round trip, and the extra submits are bounded at 6 s. No measurement of this path exists yet. Criterion 19 (§6.2) measures it and gates the rollout on it. `agentControlCallTimeout` (30 s) stays the default for other routes.

### 2.3 Queueing and ordering
- No new hub queue. The message row stays the durable intent (pkg/store/models.go:2511-2527), and reconcile still drives pending rows (pkg/hub/reconcile.go).
- Ordering is the broker's: its per-container lock is held across the RPC, so at most one flush per agent is in flight. Debounce stays at 2 s and joins messages with `\n\n`.
- Interrupts keep their current path: synchronous and unbuffered. They take the same per-container lock as today (`deliverImmediate`, pkg/agent/manager.go:1432). On the exec path an interrupt can therefore still overtake buffered messages by up to the readiness deadline (the buffer waits for readiness before it takes the lock), but never a paste already in flight. This is the current behaviour. **Amended (review round 2, P2-O1):** on the conduit path the readiness wait runs inside the hub call (gap G7), and the lock is held across that call. An interrupt that arrives during a conduit flush therefore waits behind the flush's readiness wait and paste, up to about the 90 s readiness bound, and does not overtake it. Pinned by `TestConduitDelivery_InterruptWaitsBehindFlush`.

### 2.4 Retries and dedup
- Broker retries keep today's rule: 3 attempts, 500 ms apart, **only when the failure proves the paste did not happen**. Those failures are 400*, 404, 413, 422, 429, 501 and 503, agent 409 `busy` (R3), plus `ErrNoSession`, `ErrAgentControlNotAdvertised`, and a refused or failed connection to the hub before the request was sent. (*400 is permanent: no retry, report.)
- A timeout, or a reset after the request was sent, is **ambiguous**. It is treated as `PartialDeliveryError` and is not retried, which matches "ack on successful paste, partial with no retry" (#1866). Duplicate pastes are worse than a reported partial.
- Every retry reuses the same `delivery_id`. **The hub's row state is the primary guard** (§2.6): rows bound to a delivery accept only that id, and rows past `delivering` return the stored outcome without calling the agent. A broker, or a broker bug, cannot re-paste an authorized message under a fresh id. The agent's key store (§5.5) is the second layer, for re-sends of the same id by the hub or relay.
- The hub **unbinds** the rows in the same handler (`delivering → dispatched`, compare-and-set on the `delivery_id`) whenever its own call shows that **nothing was pasted**. This is the same list as §2.6 (Q1):
  - not reached: `ErrNoSession`, `ErrAgentControlNotAdvertised`, 404, session 429/501/503, agent 409 `busy`;
  - failed before paste: 400, 413, 422, 408 `expired_before_paste`.

  A broker retry (not-reached cases) or an exec fallback (for example after 413) can then proceed, and the exec path leaves the rows in `dispatched` as today. Only `delivered`, `partial`, agent 409 `in_progress`, and a timeout or reset after send keep or finalise the binding. So a 413 followed by exec ends as the exec path's outcome, never as `partial` from the stale sweep.
- The hub does not retry this route. `dispatchWithBrokerRetry` (pkg/hub/broker_routing.go:154) is unchanged and only retries `ErrMessageDeferred`.

### 2.5 Before the session is up
Early in start there is no session (`ErrNoSession`). The broker retries as above, then falls back to exec when the runtime has it (docker, Kubernetes, Cloud Run with an IAP connector). With no exec, it reports a failure before paste and the row is marked failed, as an exec failure is today. A "hold until the session is admitted" re-drive is **deferred** (§6.4); this design does not need it. **Frozen by D11 = (b)** (ptone, msg 92c52dc8): Phase A does not hold or queue a message until the session connects. Hold-until-session is follow-up ptone/scion#7881.

### 2.6 Row binding and state machine (sec Required)
The `dispatch_state` column (pkg/store/models.go:2511-2527: `pending`, `dispatched`, `failed`, `deferred`, `no_recipient`) gains three states: `delivering`, `delivered` and `partial`. It also gains three columns:
- `delivery_id`, the bound id;
- `delivering_at`, the bind time, used by the stale sweep;
- `delivery_outcome`, the stored outcome JSON (`outcome`, `stage`), which the hub returns on a same-id replay. It is written by the same compare-and-set as the final state and holds no text. Today's transitions are unchanged; `MarkMessageDispatched` (pkg/store/entadapter/brokerdispatch_store.go:277) is already a compare-and-set.

```
pending ──(existing dispatch)──▶ dispatched ──(/deliver bind, 1 tx, all rows)──▶ delivering[id]
delivering[id] ──agent 200 delivered──▶ delivered
delivering[id] ──agent 200 partial / 409 in_progress / timeout or reset after send──▶ partial
delivering[id] ──proved not reached (hub call)──▶ dispatched           (compare-and-set on id; retry or exec may follow)
delivering[id] ──agent 409 busy──▶ dispatched                           (not reached; compare-and-set on id)
delivering[id] ──agent 400 / 413 / 422 / 408 expired_before_paste (failed before paste)──▶ dispatched; then exec fallback, or the broker reports ──▶ failed
delivering[id] ──stale: delivering_at older than 2 × 110 s──▶ partial  (reconcile; never re-driven)
dispatched ──exec path (unchanged)──▶ dispatched / failed               (as today)
```

Rules:
- **Bind** is one transaction: `UPDATE ... SET dispatch_state='delivering', delivery_id=?, delivering_at=now WHERE id IN (...) AND recipient=agent AND dispatch_state='dispatched'`. It must affect exactly `len(message_ids)` rows, or it rolls back and the hub answers 409 `bound`.
- ~~**Same-id retry** on rows that are all `delivering[id]`: forwarded. The agent replays or runs it, and §5.5 dedups.~~ **Amended (review round 1, R1):** a same-id call on rows that are all `delivering[id]` is answered 409 `in_flight` (round 2, FV1-N1; round 1 used `in_progress`) and is **not** forwarded. The call that bound the rows is the delivery's only owner, across hub replicas, and only the owner calls the agent and unbinds or finishes the rows. Otherwise a duplicate's own not-reached answer (for example a session-level 503) would unbind rows the owner is still pasting, and a fresh id could then paste them again. A same-id retry after the owner's unbind (nothing pasted) finds the rows `dispatched` and binds again as the new owner. The broker ends a call answered `in_flight` without an error and without a failure report: no retry and no exec fallback, and the owner stays responsible for the rows (round 2, FV1-N1).
- **Rows in a final state** (`delivered`, `partial`, `failed`) **under the same id**: the hub answers 200 with the stored outcome and `replayed:true`, and does not call the agent. **Under another id**: 409 `bound`, not forwarded.
- **Hub restart mid-delivery:** the in-flight call is lost. The broker sees a reset after send and treats it as partial with no retry (§2.4). On startup and on each reconcile pass, rows in `delivering` with `delivering_at` older than 220 s (2 × 110 s) move to `partial` with reason `outcome unknown`. They are never moved back to `dispatched` and never re-driven, because the paste may have happened. reconcile (pkg/hub/reconcile.go) must also skip `delivering`, `delivered` and `partial` when it drains pending rows.
- **Outcome writes** are compare-and-set on (`delivering`, `delivery_id`), so a late outcome cannot overwrite the stale sweep's result.
- The **exec path** never binds, so its behaviour is unchanged. It still cannot dedup broker re-sends; that existing limit is noted, not widened.

## 5. AuthZ: sec-review-3's seven points

**5.1 Authority (authorize before Call(agent)).** The user's authority is checked once, at `POST /api/v1/agents/{id}/message`. The chain is `admitDelegatedAgentHandler`, `rejectRetiredRawMessageBody`, then `authorizeAgentMessage` (pkg/hub/authorize_message.go:281; permission `agent.message`, :327; catalog `agent.action.message`, pkg/hub/authzop/catalog_agents.go:514), with 403 `ErrCodeMessageDenied` on deny. This is the same check `scion message` uses. The message row is written only after that check passes.

The broker → hub `/deliver` call adds **no new user-facing authority**. Before any `Call(agent)`, it is accepted only if:
- the caller is the agent's current broker;
- every message id names a row that passed that check, targets this agent, and is in `dispatched`.

**Interrupt** is message-level, as today: the `interrupt` flag on the message API, permission `agent.message`. **Raw keys** are not on this route. They stay on the separate `/keys` route with its current authorization (§3.3).

**Content trust (fix2-rev Consider, accepted).** The hub binds rows and ids, but it **cannot verify that the text the broker sends equals the bound rows' text**. Debounce joins several messages, and delivery text can differ from the stored body. The broker is trusted for content, exactly as it is with exec today. This design adds no new content authority: the broker could already paste anything over exec. An optional cheap check, not required: the hub records the total byte length of the bound rows at bind time and logs it next to the request's text length, as a drift signal only.

**5.2 Channel.** The route is reachable only as an `RpcRequest` frame on the session sciontool dialed outbound to the hub. That session is authenticated at upgrade with the agent token (pkg/sciontool/conduit/agent.go, Hello at :361) and admitted by the hub (`decideConduitAgent`, pkg/hub/conduit_relay.go:652).
- There is no new listener: `control.New` is called once, and the handler is wired only as the session's RPC target (cmd/sciontool/commands/init_conduit.go:93-116).
- There is no loopback or local HTTP route.
- An in-container process cannot inject frames into sciontool's session. Frames flow hub→agent on a connection sciontool owns.
- The route gives that process nothing it lacks already: it can reach the agent's own tmux directly, as the same container user. The only principal the route adds is the hub relaying an authorized message.
- Tested: the route is absent from every non-session surface (§6.3).

**5.3 No generic exec.**
- Data only, against a fixed schema (§1.2). Unknown fields → 400.
- The tmux target is the sciontool constant `scion:0`. The buffer name is built by sciontool from a validated `delivery_id`.
- Commands are run with `exec.Command("tmux", fixed-verb, ...)`: no shell and no caller-supplied argv. The text goes only through stdin to `load-buffer`, and is pasted bracketed.
- **Text sanitising (Consider-1, taken).** Before `load-buffer`, the shared package (§3.4) removes the bracketed-paste markers `ESC[200~` and `ESC[201~`, and every other C0 control except `\n` and `\t`, including `ESC` itself and `\r`. It also removes DEL (0x7f) and the **C1 controls U+0080 to U+009F**. U+009B is the 8-bit CSI that some terminal parsers accept as `ESC[` (sec Consider, r3). Text is handled as UTF-8 code points, so C1 means those code points, not raw bytes inside multi-byte characters. Invalid UTF-8 is replaced with U+FFFD before the strip. Pasted text therefore cannot end paste mode early and be read as typed keys. The sender already holds `agent.message`, so this adds no authority; it keeps paste semantics exact.
  - **Today's `deliverImmediate` does not do this.** It wraps the text in bracketed paste (`paste-buffer -p`, pkg/agent/manager.go:1519-1546) but passes the text through unchanged.
  - The sanitiser is applied on **both** paths through the shared package, so exec and conduit behave identically. It is a visible change on the exec path, for message text that contains control characters, and is listed in the rollout notes.
- Keys must match an allowlist of tmux key names: `Enter`, `Escape`, `Tab`, `C-c`, `C-d`, `C-j`, `C-m`, `C-u`. At most 4 per list. No literal strings and no `-l`. The shipped harnesses use only `Enter`, `Escape` and `C-c` (§1.7). Anything outside the list goes to exec, or fails with a named field; it is never clamped (R2).
- There is no tmux command passthrough: no `run-shell`, no `if-shell`, and no `-t` from the request.

**5.4 Attachments.** v1: the route accepts **no attachments** and never writes to the filesystem outside tmux's own buffer (§1.6). A later `deliver-attachment` route must reuse the existing broker rules as the minimum:
- id `^[A-Za-z0-9-]{1,64}$`; name `^[A-Za-z0-9_][A-Za-z0-9._-]{0,119}$`; size and sha256 verified (pkg/runtimebroker/inbox.go:98-101, :255);
- writes only under `~/.scion/inbox/<message-id>/`, created with `O_EXCL`, opened `O_NOFOLLOW`, no symlinks, written to a temp file and renamed into place; an existing directory means "already delivered";
- caps on both sides: hub 10 MB and 10 files per message (pkg/hub/attachments.go:77-79) plus `attachment_delivery_max_bytes`; the agent enforces the same caps again;
- any path outside the inbox → reject.

**5.5 Idempotency key: two layers.**
- **Layer 1, the hub row state (primary, sec Required).** The hub binds the delivery to its message rows atomically (§2.6): `dispatched → delivering[delivery_id]`, all rows or none. Rows bound to an id accept only that id. Rows in a final state return the stored outcome with `replayed:true` and **never reach `Call(agent)`**. A broker, or a broker bug, therefore cannot re-paste an authorized message under a fresh `delivery_id`. A stale `delivering` row becomes `partial` and is never re-driven.
- **Layer 2, the agent key store (defence in depth).** The key is (`agent`, hub-set `broker_id`, `delivery_id`). The store keeps at most 1024 entries, LRU, with a 15-minute TTL, and holds only the outcome, never the text. A replay of a finished key returns the stored outcome with `replayed:true` and never re-pastes; a replay of a running key gets 409. It covers re-sends of the same id by the hub or relay.
- Retries come only from the broker's proven-not-reached rule (§2.4) and always reuse the bound id. Key replay is never the reason to retry (O2).
- A sciontool restart means a new tmux server and harness. The agent store is lost, but layer 1 still holds, and the broker treats the in-flight flush as partial.

**5.6 Logging and audit.** Info lines carry the delivery and its outcome:
- hub: caller broker, agent id, project, message id count, text byte size, op, outcome, latency;
- agent: `delivery_id`, byte size, op, outcome, stage, replayed.

**Never at info:** the text, attachment names or contents, or key names (debug only, and only allowlisted names). Error bodies are fixed strings with a stage. No tokens, ids of other tenants, or text appear in errors.


**5.7 Cross-tenant.** The agent is resolved from the URL path through the store, never from the body. The hub:
- checks the path broker is the agent's current broker;
- checks every message row belongs to that agent, and through it to its project;
- overwrites `broker_id`;
- routes by the hub-resolved agent id to that agent's admitted session.

The agent ignores any identity field except the hub-set `broker_id`, and only uses it for key scoping.

### 6.2 Criterion 19

  The `not_after` bound (Q3b) is the primary guard; this bar is the backstop. If any bar fails, lower `MaxDeliverText`, raise the hub timeout (keeping it under the relay's 120 s), or reduce queueing before Phase A goes ahead.

### 6.4 Failure modes
| failure | result |
|---|---|
| session not up | proven-not-reached → retry, then exec fallback or reported failure |
| session drops after the request was sent | ambiguous → partial, no retry; the row shows partial |
| relay owner moves mid-call | router re-resolves before send (proven-not-reached); after send → ambiguous |
| harness never ready | after the readiness timeout (≤ 90 s), the paste goes ahead anyway (current behaviour) |
| readiness plus queueing pass the hard stop | 408 `expired_before_paste`: nothing pasted, the rows are unbound, and the broker reports a failure before paste (R3) |
| agent clock far ahead of the hub's | the skew guard ignores `not_after`; the receipt bound is used and the delivery pastes; a skew warning is counted |
| send-to-receipt delay over the assumption, and the `not_after` bound defeated by skew | a late paste on rows already `partial`, never a duplicate; the next flush gets `busy` and retries (§2.2) |
| a different flush is still running on the agent | agent 409 `busy`: not reached, retried under the pre-paste rule (R3) |
| tmux target gone, or staging (load-buffer) fails | 422 → retry, then a failure before paste |
| oversize text | 413 → exec, or reported failure |
| sciontool restart mid-flush | ambiguous → partial; the key store is lost along with the session |
| hub restart mid-call | the broker sees a reset after send → partial; the hub's stale sweep moves `delivering` rows to `partial` after 220 s, never back to `dispatched` (§2.6) |
| broker bug re-sends under a fresh id | hub 409 `bound`; the agent is never called (§2.6) |
| experiment flipped off mid-flight | the route stays registered until restart; the hub `/deliver` returns 404 → exec fallback |
| deferred: hold until session admission | not in v1 (D11 = b); follow-up ptone/scion#7881 |
